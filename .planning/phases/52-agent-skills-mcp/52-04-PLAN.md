**ironclaw-routes.ts** — Add endpoint:

`POST /api/ironclaw/suggestions/:id/accept`
Body: `{ problemSetId, targetField, fieldValue }`

Handler logic:
1. Validate the suggestion ID exists in the message store (query ironclaw_messages where suggestion->>'id' = :id)
2. Check user's role permissions for the target field. Import the problem set membership from the request context. Use a `ROLE_FIELD_PERMISSIONS` map:
   - Commander/XO: can write all fields (`'*'`)
   - J2: intelligence-related fields (`'design.problemFraming', 'design.cogAnalysis.*', 'intelligence.*'`)
   - J3: operations fields (`'design.operationalApproach', 'design.linesOfEffort', 'plan.coaDetails.*'`)
   - J5: planning fields (`'design.*', 'plan.*'`)
   - Default: reject with 403
3. If `targetField` is in SENSITIVE_FIELDS, check that a Decision Gate has been approved for this suggestion (query decision_gates table). If not, return 403 with message "Requires Decision Gate approval".
4. Dispatch field write to the correct API. Use a `FIELD_WRITE_DISPATCH` map:
   - `'name'` / `'description'` → `PATCH /api/problem-sets/:id` (internal function call, not HTTP)
   - `'design.*'` → call the design API update function (PUT /api/design/:psId/...)
   - `'missionStatement'` / `'commandersIntent'` → problem set metadata update
   - For unknown fields, attempt generic `PATCH /api/problem-sets/:id/fields` with `{ [targetField]: fieldValue }`
5. Return 200 with `{ applied: true, field: targetField }` on success
