  <name>Task 1: AI agent resource tools and telemetry service</name>
  <files>backend/src/graph/tools/resource-tools.ts, backend/src/resources/resource-telemetry.ts</files>
  <action>
1. **Create `backend/src/graph/tools/resource-tools.ts`:**
   Follow the raft-tools.ts MCPToolInput pattern. Define 3 tool definitions:

   a. `find_resources_by_capability`:
      - description: "Find resources with a specific capability (e.g., ISR, CASEVAC, air_defense, SIGINT). Returns resources matching the capability tag."
      - inputSchema: { capability: string (required), missionId: string (optional) }
      - Handler: getResourceRegistry().findByCapability(capability), optionally filter by missionId
      - Return: array of { id, name, category, status, did, capabilities, location }

   b. `find_resources_in_area`:
      - description: "Find resources within a geographic bounding box. Useful for identifying assets near an area of operations."
      - inputSchema: { north: number, south: number, east: number, west: number (all required) }
      - Handler: getResourceRegistry().findInArea(bounds)
      - Return: array of { id, name, category, status, location, capabilities }

   c. `get_resource_status`:
      - description: "Get detailed status and capabilities for a specific resource by ID or DID."
      - inputSchema: { resourceId: string (optional), did: string (optional) } — at least one required
      - Handler: if did provided, use getByDID(); else use getResource(id)
      - Return: full resource details including specifications, capabilities, group, trust tier

   Export as `resourceToolDefinitions: MCPToolInput[]`.

2. **Create `backend/src/resources/resource-telemetry.ts`:**
   Singleton service for telemetry ingestion and batched WebSocket push.

   **Class: ResourceTelemetryService**
   - `private pendingPositions: Map<string, TelemetryFrame>` where TelemetryFrame = { lat, lng, heading?, speed?, timestamp }
   - `private batchInterval: ReturnType<typeof setInterval> | null`
   - `private BATCH_INTERVAL_MS = 3000` (3 second batches per research recommendation)

   - `start(): void` — sets up setInterval that calls `flushPositions()` every 3 seconds
   - `stop(): void` — clears interval

   - `ingestTelemetry(resourceId: string, data: { lat: number; lng: number; heading?: number; speed?: number }): void`:
     - Add to pendingPositions map (latest overwrites previous for same resource)
     - Update resource location in registry cache (write-through to DB via registry)
     - Get plugin for resource, call plugin.processTelemetry() if defined (fire-and-forget)

   - `private flushPositions(): void`:
     - If pendingPositions.size === 0, return
     - Build batch payload: `{ type: 'resource:position_batch', positions: Object.fromEntries(pendingPositions) }`
     - Import MessageBus from messaging and publish to `resource:positions` channel
     - Clear pendingPositions map

   - Singleton: `export function getResourceTelemetryService(): ResourceTelemetryService`

   Note: Import MessageBus from `backend/src/messaging/message-bus.ts`. If MessageBus doesn't have a generic broadcast, use the WebSocket server from messaging API to broadcast. Check what pattern is used by the existing messaging infrastructure and follow it.

<task type="auto">
  <name>Task 2: Extended REST API routes for registry, groups, and telemetry</name>
  <files>backend/src/api/resources.ts</files>
  <action>
Extend the existing `backend/src/api/resources.ts` router with new endpoints. Keep ALL existing endpoints unchanged. Add new endpoints AFTER existing ones:

**Registry Query Endpoints:**
1. `GET /registry/search` — search registry with query params:
   - `capability` (string) -> findByCapability()
   - `category` + `status` (strings) -> findByTypeAndStatus()
   - `north,south,east,west` (numbers) -> findInArea()
   - `did` (string) -> getByDID()
   - Returns: `{ resources: RegisteredResource[] }`

2. `GET /registry/capabilities` — list all known capabilities across all plugins:
   - Aggregate from PluginRegistry.getAllPlugins()
   - Returns: `{ capabilities: string[] }`

3. `GET /registry/stats` — registry statistics:
   - Total resources, by category, by status, by autonomous/passive
   - Returns: `{ total, byCategory: Record<string,number>, byStatus: Record<string,number>, autonomous, passive }`

**DID Endpoints:**
4. `GET /did/:did` — resolve resource by DID:
   - URL-decode the DID parameter
   - Returns: RegisteredResource or 404

**Group Endpoints:**
5. `GET /groups?missionId=X` — list groups for a mission
6. `POST /groups` — create group: { missionId, name, groupType, description?, parentGroupId? }
7. `GET /groups/:groupId` — get group with member count
8. `GET /groups/:groupId/members` — list group members
9. `POST /groups/:groupId/members` — add resource to group: { resourceId }
10. `DELETE /groups/:groupId/members/:resourceId` — remove resource from group
11. `DELETE /groups/:groupId` — delete group (unassigns members first)

**Telemetry Endpoint:**
12. `POST /telemetry` — ingest telemetry: { resourceId, lat, lng, heading?, speed? }
    - Calls getResourceTelemetryService().ingestTelemetry()
    - Returns 202 Accepted (async processing)

**Registration Endpoint:**
13. `POST /registry/register` — register resource with full plugin treatment:
    - Body: ResourceManifest (name, category, missionId, specifications, isAutonomous, capabilities)
    - Validates via plugin, generates DID, stores in registry
    - Returns 201 with RegisteredResource

Import getResourceRegistry, resourceGroupStore, getResourceTelemetryService, getPluginRegistry at top.

Note: Register static routes (/registry/*, /groups, /did/*, /telemetry) BEFORE parametric routes (/:id, /:id/status) to prevent Express route shadowing — same pattern as Phase 19 Plan 03 decision.
