Extend the robot-mission-service.ts (created in Plan 01) with gate integration:

**Add gate creation on awaiting_auth:**
- In `handleStateUpdate()`, when state transitions to `awaiting_auth`:
  1. Look up the mission from DB to get problem_set_id
  2. Import and call `getGateService().createGate()` with:
     - `problem_set_id`: from mission record
     - `gate_type`: GateType.robot_action_auth
     - `target_item_id`: mission_id
     - `target_item_type`: 'robot_mission'
     - `target_item_title`: `Robot Authorization — ${metadata.action || 'restricted action'} — Mission ${mission_id}`
     - `enforcement`: GateEnforcement.hard_block
     - `mode`: 'operational' (or read from problem set context if available)
  3. Store the gate_id in the robot_missions record (update via robotStore)
  4. Log gate creation

**Add gate resolution listener:**
- Add method `handleGateResolution(gateId: string, approved: boolean)`:
  1. Find the mission associated with this gate_id (query robotStore)
  2. Find the connected robot for that mission
  3. Send WS message to robot: `{ type: "auth:response", mission_id, approved }`
  4. If approved, update mission state to "executing" in DB
  5. If denied, update mission state to "failed" with reason "authorization_denied"

**Add gate polling/subscription:**
- For MVP, add a simple periodic check (every 2 seconds) that polls for resolved gates related to robot missions. Check if any gate_id in active awaiting_auth missions has been approved/rejected via `getGateService()`.
- Alternative (preferred if straightforward): Hook into gate-service event emitter if one exists. If not, the polling approach is acceptable for MVP.

**Update handleStateUpdate to broadcast state changes:**
- After updating mission state in DB, emit the state change so Plan 04 (COP layer) can consume it. For now, store latest state in the in-memory connectedRobots map. The COP layer will query this via `getMissionStatus()`.
