## Decisions Made

**Sensor API Endpoint Granularity:**
- Created specialized endpoints for status-only and location-only updates instead of forcing full PATCH
- Rationale: Tactical systems need atomic updates (e.g., sensor goes offline without changing location)
- Coverage endpoint returns calculated circles instead of stored polygons for simplicity

**Military Symbology Library:**
- Used milsymbol library with MIL-STD-2525D SIDC codes
- Rationale: Industry standard with 1000+ symbols, generates SVG in <20ms, no dependencies
- createMilSymbolIcon helper wraps milsymbol Symbol as Leaflet DivIcon

**Sensor Coverage Rendering:**
- Rendered as Leaflet Circle with radius from sensor.capabilities.range
- Color-coded by category (airborne=blue, ground=green, maritime=cyan, space=purple, autonomous=orange)
- Opacity reflects operational status (operational=0.3, degraded=0.2, offline=0.1, maintenance=0.15)
- Rationale: Simpler than polygon editing, sufficient for initial visualization

**Real-time Tracking Infrastructure:**
- Created RealtimeTracker component with WebSocket client logic
- WebSocket server NOT implemented in this plan (future phase)
- Rationale: Prepare client infrastructure while server integration deferred to ATAK/CoT phase (4.5)

**Layer Control Structure:**
- Category-based toggles for sensors (5 categories: airborne, ground, maritime, space, autonomous)
- Separate toggles for resources by type (weapon_system, vehicle, equipment, communication)
- Rationale: Tactical users need fine-grained control over map density
