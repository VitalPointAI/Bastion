# Phase 25.2: Strategic Document Containers & Actor Categorization - Research

**Researched:** 2026-03-06
**Domain:** Data modeling, hierarchical UI, drag-and-drop, container management
**Confidence:** HIGH

## Summary

Phase 25.2 introduces a container-based organizational layer on top of the existing flat `strategic_documents` table. The work spans four areas: (1) new PostgreSQL tables for strategic environments, actor categories, containers, and junction tables; (2) extending the upload pipeline to support container assignment; (3) replacing the flat DocumentList with a container-browsing UI; and (4) adding container-level agent assignments as "standing orders."

The existing codebase follows a clear pattern: Express routes in `backend/src/api/`, store classes with `initTable()` lazy initialization, frontend React components consuming a singleton service class (`strategicService`). The project already uses `react-hook-form` and `@tanstack/react-table` but has no drag-and-drop library installed. The assignment system is currently in-memory (`Map`-based) -- container agent assignments should follow the same pattern or optionally move to PostgreSQL.

**Primary recommendation:** Build four new PostgreSQL tables (`strategic_environments`, `actor_categories`, `strategic_containers`, `container_documents`) with a store class following the `DocumentStore` pattern. Use `@dnd-kit/core` + `@dnd-kit/sortable` for drag-and-drop (React 19 compatible, lightweight). Refactor `StrategicDashboard` internals to add a container browser view while preserving the existing document detail flow.

### Pattern 1: Lazy Table Initialization (Existing)
**What:** Tables are created via `initTable()` on first API request
**When to use:** All new tables (strategic_environments, actor_categories, strategic_containers, container_documents, container_agent_assignments)
**Example:**
```typescript
// Source: backend/src/strategic/ingestion/document-store.ts (existing pattern)
export async function initContainerTables(): Promise<void> {
  const pool = getPool();

  await pool.query(`
    CREATE TABLE IF NOT EXISTS strategic_environments (
      id TEXT PRIMARY KEY,
      name TEXT NOT NULL,
      description TEXT,
      created_by TEXT NOT NULL,
      created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
      updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    )
  `);

  await pool.query(`
    CREATE TABLE IF NOT EXISTS actor_categories (
      id TEXT PRIMARY KEY,
      environment_id TEXT NOT NULL REFERENCES strategic_environments(id) ON DELETE CASCADE,
      name TEXT NOT NULL,
      color TEXT NOT NULL,
      display_order INTEGER NOT NULL DEFAULT 0,
      is_default BOOLEAN NOT NULL DEFAULT false,
      created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
      UNIQUE(environment_id, name)
    )
  `);

  await pool.query(`
    CREATE TABLE IF NOT EXISTS strategic_containers (
      id TEXT PRIMARY KEY,
      environment_id TEXT NOT NULL REFERENCES strategic_environments(id) ON DELETE CASCADE,
      category_id TEXT NOT NULL REFERENCES actor_categories(id) ON DELETE CASCADE,
      name TEXT NOT NULL,
      description TEXT,
      created_by TEXT NOT NULL,
      created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
      updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    )
  `);

  await pool.query(`
    CREATE TABLE IF NOT EXISTS container_documents (
      id TEXT PRIMARY KEY,
      container_id TEXT NOT NULL REFERENCES strategic_containers(id) ON DELETE CASCADE,
      document_id TEXT NOT NULL,
      assigned_by TEXT NOT NULL,
      assigned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
      UNIQUE(container_id, document_id)
    )
  `);

  await pool.query(`
    CREATE TABLE IF NOT EXISTS container_agent_assignments (
      id TEXT PRIMARY KEY,
      container_id TEXT NOT NULL REFERENCES strategic_containers(id) ON DELETE CASCADE,
      agent_id TEXT NOT NULL,
      assignment_type TEXT NOT NULL DEFAULT 'monitor',
      auto_process_new BOOLEAN NOT NULL DEFAULT true,
      assigned_by TEXT NOT NULL,
      assigned_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
      UNIQUE(container_id, agent_id)
    )
  `);
}
```

### Anti-Patterns to Avoid
- **Denormalizing container data into strategic_documents:** Documents belong to containers via junction table, NOT by adding a container_id column to strategic_documents (since documents can belong to multiple containers)
- **Coupling containers to problem sets directly:** Containers are scoped to strategic environments, not problem sets. The problem-set-to-environment relationship comes in Phase 26
- **Building a custom drag-and-drop system:** Use @dnd-kit -- the edge cases (touch, accessibility, scroll zones, collision detection) are extensive
- **Storing category colors in CSS:** Store colors in the database with the category record so custom categories work without code changes

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Drag and drop | Custom mouse event handlers | @dnd-kit/core | Touch support, accessibility (ARIA), collision detection algorithms, scroll containers |
| Multi-select dropdown | Custom checkbox list | `<select multiple>` with grouped `<optgroup>` or custom component with checkboxes | Keyboard navigation, screen reader support |
| Color picker for custom categories | HSL sliders | Predefined palette of 12-16 colors | Military context favors recognizable colors; free-form pickers create unusable schemes |
| Audit trail for category changes | Custom event log table | `blockchain_events` table (existing) | Already has event sourcing pattern with aggregate_id, event_type, event_data |
| UUID generation | Custom ID scheme | `randomUUID()` from Node crypto | Already used throughout codebase |

**Key insight:** The existing `blockchain_events` table provides a perfect audit trail for category reassignment. Use `event_type: 'container_category_changed'` with `aggregate_id: containerId` and store old/new category in `event_data`.

## Common Pitfalls

### Pitfall 1: Orphaned Documents After Container Delete
**What goes wrong:** Deleting a container removes junction table entries, making documents invisible if they were only in that container
**Why it happens:** CASCADE delete on junction table without checking if document has other container memberships
**How to avoid:** On container delete, identify documents that would become orphaned (only in this container) and move them to "Unorganized" (remove from junction table = unorganized). Show a confirmation dialog listing affected documents.
**Warning signs:** Documents disappearing from the UI after container operations

### Pitfall 2: Strategic Environment Scoping Confusion
**What goes wrong:** Containers appear in wrong problem sets or cross-contaminate between exercises
**Why it happens:** The lightweight `strategic_environments` table must be correctly associated before Phase 26 adds full inheritance
**How to avoid:** For now, create one default strategic environment per problem set. Store the mapping. Phase 26 will formalize this.
**Warning signs:** Users seeing containers from other exercises

### Pitfall 3: N+1 Queries on Container View
**What goes wrong:** Loading container browser issues separate queries for each container's document count, agent assignments, etc.
**Why it happens:** Naive implementation fetches containers, then loops to get counts
**How to avoid:** Use aggregate queries with JOINs. Single query to get containers with document counts and agent assignment counts per category.
**Warning signs:** Slow page loads as container count grows

### Pitfall 4: AI Recommendation Blocking Upload
**What goes wrong:** Upload hangs waiting for AI to analyze document and suggest containers
**Why it happens:** AI inference takes 2-10 seconds; if synchronous, blocks the upload confirmation
**How to avoid:** Upload immediately, show document in "processing" state. AI recommendation appears asynchronously (SSE or polling) and user confirms/adjusts after. OR: run AI in parallel with upload so by the time upload completes, suggestion is ready.
**Warning signs:** Upload form feels sluggish, users skip container assignment entirely

### Pitfall 5: Drag-and-Drop State Desync
**What goes wrong:** UI shows document in new container but backend rejected the move; or vice versa
**Why it happens:** Optimistic UI update without proper rollback on API failure
**How to avoid:** Use optimistic update pattern: update UI immediately, revert on API failure with toast notification. Keep source-of-truth in server state.
**Warning signs:** Documents appearing in wrong containers after page refresh

### Container Store CRUD (Backend)
```typescript
// Source: follows pattern from backend/src/strategic/ingestion/document-store.ts
export class ContainerStore {
  async createEnvironment(name: string, createdBy: string): Promise<string> {
    const pool = getPool();
    const id = randomUUID();
    await pool.query(
      `INSERT INTO strategic_environments (id, name, created_by) VALUES ($1, $2, $3)`,
      [id, name, createdBy]
    );
    // Seed default categories
    for (const [key, meta] of Object.entries(DEFAULT_CATEGORIES)) {
      await pool.query(
        `INSERT INTO actor_categories (id, environment_id, name, color, is_default, display_order)
         VALUES ($1, $2, $3, $4, true, $5)`,
        [randomUUID(), id, meta.name, meta.color, meta.order]
      );
    }
    return id;
  }

  async getContainersGroupedByCategory(environmentId: string): Promise<CategoryGroup[]> {
    const pool = getPool();
    const result = await pool.query(`
      SELECT
        ac.id as category_id, ac.name as category_name, ac.color,
        ac.display_order, ac.is_default,
        sc.id as container_id, sc.name as container_name, sc.description,
        COUNT(cd.id)::int as document_count,
        COUNT(caa.id)::int as agent_count
      FROM actor_categories ac
      LEFT JOIN strategic_containers sc ON sc.category_id = ac.id
      LEFT JOIN container_documents cd ON cd.container_id = sc.id
      LEFT JOIN container_agent_assignments caa ON caa.container_id = sc.id
      WHERE ac.environment_id = $1
      GROUP BY ac.id, ac.name, ac.color, ac.display_order, ac.is_default,
               sc.id, sc.name, sc.description
      ORDER BY ac.display_order, sc.name
    `, [environmentId]);

    // Group rows by category
    return groupByCategory(result.rows);
  }
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Flat document list | Container-organized browsing | This phase | Documents grouped by nation/org under actor categories |
| Documents scoped to user | Documents scoped to strategic environment | This phase | Shared across problem sets |

## Open Questions

1. **Strategic Environment Discovery**
   - What we know: Need a lightweight `strategic_environments` table. Phase 26 adds inheritance.
   - What's unclear: How does a user create/select their strategic environment? Auto-create on first container creation? Explicit "Create Strategic Environment" step?
   - Recommendation: Auto-create a default strategic environment when a problem set is created (or on first container action). Allow rename but not manual creation until Phase 26.

2. **Unorganized Documents Visibility**
   - What we know: Documents not assigned to any container go to "Unorganized" section
   - What's unclear: Should "Unorganized" be a virtual container or just a filtered view? Should it appear under every category or as a separate top-level section?
   - Recommendation: Treat as a separate section below the category groups. Query: documents WHERE id NOT IN (SELECT document_id FROM container_documents).

3. **Container Agent Auto-Processing Trigger**
   - What we know: When an agent is assigned to a container, new documents should be auto-processed
   - What's unclear: Should this happen synchronously during document-to-container assignment, or via a background job queue?
   - Recommendation: Trigger asynchronously. On `container_documents` insert, check for `container_agent_assignments` with `auto_process_new = true`, then call the existing agent execution pipeline. Use the existing SSE streaming pattern for progress.

4. **Custom Category Color Palette**
   - What we know: Four defaults have fixed colors. Custom categories pick from a palette.
   - What's unclear: Exact palette size and colors
   - Recommendation: Provide 12 colors (Tailwind 600-weight): slate, red, orange, amber, emerald, teal, cyan, blue, indigo, violet, purple, pink. Exclude the 4 default colors from the custom palette to prevent confusion.
