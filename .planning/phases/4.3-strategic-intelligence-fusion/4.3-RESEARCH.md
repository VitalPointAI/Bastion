<research_summary>
## Summary

Researched the ecosystem for building a strategic intelligence fusion system that consolidates multiple strategic documents, tracks objective validity against real-world events, and provides RAFT (Relationships, Actors, Functions, Tensions) graph-based analysis for geopolitical understanding.

The standard approach uses Neo4j as the graph database (mature ecosystem, excellent TypeScript support, battle-tested at scale), combined with LangChain.js for LLM-powered knowledge graph construction from unstructured documents. Entity resolution leverages string similarity algorithms (Jaro-Winkler, Levenshtein) with LLM-assisted semantic deduplication. OSINT integration follows an event-driven architecture with modular data collection from configurable feeds.

Key finding: Neo4j's JavaScript driver (v6) provides full TypeScript support with proper type definitions. However, LangChain.js has more limited graph transformer capabilities than the Python version - the `LLMGraphTransformer` is primarily Python-only (`langchain_experimental`). For TypeScript, use `Neo4jGraph` from `@langchain/community` with custom extraction prompts or build custom graph construction using the existing Phase 4 extraction patterns.

**Primary recommendation:** Use Neo4j + neo4j-driver (v6) + @langchain/community for graph operations. Build custom graph construction on top of existing Phase 4 LLM extraction infrastructure rather than depending on Python-only LLMGraphTransformer. Use string-comparison npm package for entity similarity scoring combined with LLM semantic verification.
</research_summary>

### Pattern 1: Neo4j Client Singleton
**What:** Single Neo4j driver instance shared across application
**When to use:** Always - driver manages connection pooling
**Example:**
```typescript
// Source: Neo4j JavaScript Driver Manual
import neo4j, { Driver } from 'neo4j-driver';

let driver: Driver | null = null;

export function getNeo4jDriver(): Driver {
  if (!driver) {
    driver = neo4j.driver(
      process.env.NEO4J_URI || 'bolt://localhost:7687',
      neo4j.auth.basic(
        process.env.NEO4J_USER || 'neo4j',
        process.env.NEO4J_PASSWORD || 'password'
      )
    );
  }
  return driver;
}

export async function closeNeo4jDriver(): Promise<void> {
  if (driver) {
    await driver.close();
    driver = null;
  }
}
```

### Pattern 2: LLM-Powered Graph Construction
**What:** Use existing Phase 4 extraction patterns to build graph documents
**When to use:** Converting strategic documents to knowledge graphs
**Example:**
```typescript
// Build on Phase 4 extraction infrastructure
import { Neo4jGraph } from '@langchain/community/graphs/neo4j_graph';
import { extractObjectives } from '../strategic/extraction-service';

interface GraphDocument {
  nodes: Array<{ id: string; type: string; properties: Record<string, unknown> }>;
  relationships: Array<{ source: string; target: string; type: string; properties: Record<string, unknown> }>;
}

async function documentToGraph(documentId: string, chunks: string[]): Promise<GraphDocument> {
  const objectives = await extractObjectives(chunks);

  const nodes: GraphDocument['nodes'] = [];
  const relationships: GraphDocument['relationships'] = [];

  for (const obj of objectives) {
    // Create objective node
    nodes.push({
      id: obj.id,
      type: 'Objective',
      properties: {
        title: obj.title,
        description: obj.description,
        classification: obj.classification,
        sourceDocument: documentId
      }
    });

    // Extract and create actor nodes from objective
    const actors = await extractActors(obj.description);
    for (const actor of actors) {
      nodes.push({ id: actor.id, type: 'Actor', properties: actor });
      relationships.push({
        source: obj.id,
        target: actor.id,
        type: 'INVOLVES',
        properties: { role: actor.role }
      });
    }
  }

  return { nodes, relationships };
}
```

### Pattern 3: Entity Resolution Pipeline
**What:** Multi-stage deduplication with similarity scoring + LLM verification
**When to use:** Merging entities from multiple documents
**Example:**
```typescript
// Source: Entity resolution best practices
import { JaroWinkler, Levenshtein } from 'string-comparison';

interface EntityCandidate {
  id: string;
  name: string;
  aliases: string[];
  sourceDocument: string;
}

interface MatchResult {
  entity1: EntityCandidate;
  entity2: EntityCandidate;
  similarityScore: number;
  matchType: 'exact' | 'fuzzy' | 'semantic';
}

function findCandidateMatches(
  entities: EntityCandidate[],
  threshold: number = 0.85
): MatchResult[] {
  const matches: MatchResult[] = [];

  for (let i = 0; i < entities.length; i++) {
    for (let j = i + 1; j < entities.length; j++) {
      const e1 = entities[i];
      const e2 = entities[j];

      // Check exact match first
      if (e1.name.toLowerCase() === e2.name.toLowerCase()) {
        matches.push({ entity1: e1, entity2: e2, similarityScore: 1.0, matchType: 'exact' });
        continue;
      }

      // Fuzzy match with Jaro-Winkler (good for names)
      const jwScore = JaroWinkler.similarity(e1.name, e2.name);
      if (jwScore >= threshold) {
        matches.push({ entity1: e1, entity2: e2, similarityScore: jwScore, matchType: 'fuzzy' });
        continue;
      }

      // Check aliases
      for (const alias of [...e1.aliases, ...e2.aliases]) {
        const aliasScore = JaroWinkler.similarity(
          e1.name.toLowerCase(),
          alias.toLowerCase()
        );
        if (aliasScore >= threshold) {
          matches.push({ entity1: e1, entity2: e2, similarityScore: aliasScore, matchType: 'fuzzy' });
          break;
        }
      }
    }
  }

  return matches;
}

// LLM verification for semantic matches (borderline cases)
async function verifySemanticMatch(
  entity1: EntityCandidate,
  entity2: EntityCandidate
): Promise<boolean> {
  // Use existing LLM infrastructure from Phase 4
  const prompt = `Are these two entities referring to the same real-world entity?
Entity 1: ${entity1.name} (aliases: ${entity1.aliases.join(', ')})
Entity 2: ${entity2.name} (aliases: ${entity2.aliases.join(', ')})

Answer only YES or NO.`;

  const response = await llmComplete(prompt);
  return response.trim().toUpperCase() === 'YES';
}
```

### Pattern 4: RAFT Graph Model
**What:** Model geopolitical relationships using RAFT framework
**When to use:** Strategic environment analysis
**Example:**
```typescript
// RAFT: Relationships, Actors, Functions, Tensions
// Source: Military operational design doctrine (ATP 5-0.1)

interface Actor {
  id: string;
  name: string;
  type: 'nation' | 'organization' | 'individual' | 'non_state_actor';
  attributes: Record<string, unknown>;
}

interface Relationship {
  id: string;
  sourceActorId: string;
  targetActorId: string;
  type: 'alliance' | 'conflict' | 'dependency' | 'competition' | 'cooperation';
  strength: number; // -1.0 (hostile) to 1.0 (allied)
  function: string; // What role this relationship serves
}

interface Tension {
  id: string;
  actorIds: string[];
  description: string;
  intensity: 'low' | 'medium' | 'high' | 'critical';
  domain: 'political' | 'military' | 'economic' | 'social' | 'information';
}

// Cypher schema for RAFT graph
const RAFT_SCHEMA = `
CREATE CONSTRAINT actor_id IF NOT EXISTS FOR (a:Actor) REQUIRE a.id IS UNIQUE;
CREATE CONSTRAINT tension_id IF NOT EXISTS FOR (t:Tension) REQUIRE t.id IS UNIQUE;

// Actor relationships
// (Actor)-[:ALLIED_WITH {strength, since}]->(Actor)
// (Actor)-[:CONFLICTS_WITH {intensity, domain}]->(Actor)
// (Actor)-[:DEPENDS_ON {dependency_type}]->(Actor)
// (Actor)-[:COMPETES_WITH {domain}]->(Actor)

// Actor functions (DIME framework)
// (Actor)-[:HAS_FUNCTION {domain: 'diplomatic|informational|military|economic'}]->(:Function)

// Tensions
// (Tension)-[:INVOLVES]->(Actor)
// (Objective)-[:ADDRESSES]->(Tension)
`;
```

### Anti-Patterns to Avoid
- **Processing chunks independently without entity resolution:** Creates massive duplication
- **Using Python LLMGraphTransformer in TypeScript project:** No direct equivalent - build custom extraction
- **Storing graph in PostgreSQL with adjacency lists:** Use proper graph database for traversals
- **Real-time LLM calls for every similarity check:** Use string algorithms for filtering, LLM for verification only
- **Monolithic fusion agent:** Split into single-responsibility agents per roadmap architecture

<dont_hand_roll>
## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Graph storage/traversal | Custom adjacency tables in PostgreSQL | Neo4j | Graph algorithms, Cypher query language, native traversal optimization |
| String similarity | Custom edit distance | string-comparison npm package | Tested implementations of Jaro-Winkler, Levenshtein, etc. |
| Graph algorithms | Custom centrality, clustering | Neo4j GDS (Graph Data Science) | PageRank, Louvain clustering, pathfinding all built-in |
| Natural language → Cypher | Custom query generation | @langchain/community GraphCypherQAChain | LLM-powered query generation with schema awareness |
| Job scheduling | Custom cron/timers | pg-boss (already in stack) | Reliable job queue with retry, dead letter, etc. |
| Entity deduplication at scale | Pairwise comparison O(n²) | Blocking + Zingg-style active learning | Blocking reduces comparisons to manageable scale |

**Key insight:** Graph operations, string similarity, and entity resolution are well-solved problems with decades of research. Neo4j implements proper graph algorithms. String similarity libraries implement peer-reviewed algorithms. Fighting these leads to correctness bugs and performance issues that are hard to debug.

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: O(n²) Entity Comparison
**What goes wrong:** Comparing every entity pair becomes infeasible at scale
**Why it happens:** Naive pairwise comparison grows quadratically with entity count
**How to avoid:** Use blocking/indexing to reduce candidate pairs (e.g., block by first letter, entity type)
**Warning signs:** Entity resolution taking minutes for hundreds of entities

### Pitfall 2: Graph Duplication from Independent Chunk Processing
**What goes wrong:** Same actor extracted from multiple chunks creates duplicate nodes
**Why it happens:** Each chunk processed independently without cross-referencing
**How to avoid:** Extract to staging area, run entity resolution, then merge to graph
**Warning signs:** Graph contains "United States", "US", "USA", "America" as separate nodes

### Pitfall 3: Neo4j Integer Handling in JavaScript
**What goes wrong:** Large Neo4j integers (64-bit) overflow JavaScript Number
**Why it happens:** JavaScript safely handles integers only up to 2^53-1
**How to avoid:** Use neo4j.integer.toNumber() only when safe, or convert to string for IDs
**Warning signs:** IDs or counts returning wrong values for large numbers

### Pitfall 4: Missing Graph Schema/Constraints
**What goes wrong:** Duplicate nodes, orphan relationships, inconsistent data
**Why it happens:** Neo4j allows schema-free operation by default
**How to avoid:** Define constraints (unique IDs) and indexes upfront
**Warning signs:** Queries returning unexpected duplicates, slow lookups

### Pitfall 5: Synchronous OSINT Processing
**What goes wrong:** UI blocks while waiting for OSINT feed responses
**Why it happens:** Processing feeds in request handler instead of background
**How to avoid:** Use pg-boss queue for feed collection, WebSocket/SSE for updates
**Warning signs:** API timeouts, frozen UI during validity updates

### Pitfall 6: LangChain.js vs Python Feature Gap
**What goes wrong:** Expecting Python LLMGraphTransformer to work in TypeScript
**Why it happens:** LangChain.js has subset of Python features
**How to avoid:** Build custom graph construction using existing extraction infrastructure
**Warning signs:** Import errors for `langchain_experimental`, missing methods
</common_pitfalls>

async function createRAFTRelationship(
  sourceActorId: string,
  targetActorId: string,
  relationType: string,
  properties: Record<string, unknown>
): Promise<void> {
  const driver = getNeo4jDriver();

  await driver.executeQuery(
    `MATCH (a:Actor {id: $sourceId})
     MATCH (b:Actor {id: $targetId})
     MERGE (a)-[r:${relationType}]->(b)
     SET r += $properties
     RETURN r`,
    {
      sourceId: sourceActorId,
      targetId: targetActorId,
      properties
    }
  );
}
