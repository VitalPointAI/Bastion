## Decisions Made

**1. Composite key pattern for mission-scoped storage**
- Use "mission_id:assumption_id" composite keys in LookupMap
- Separate mission_assumptions map tracks IDs per mission for efficient listing
- Rationale: Efficient mission-scoped queries without full storage scan

**2. Return SensitivityLevel from invalidate_assumption**
- Caller receives sensitivity level to decide replanning trigger
- Per INVARIANT 6: Critical sensitivity → create replanning gate
- Rationale: Keep registry focused on assumption lifecycle, delegate replanning logic to workflow engine

**3. Inclusive threshold filtering in all_accepted_at_sensitivity**
- Filter checks `sensitivity >= min_sensitivity` (not equality)
- Example: min_sensitivity=High checks High and Critical assumptions
- Rationale: Phase transitions require all assumptions above threshold accepted, not just exact matches

**4. BorshStorageKey enum for storage initialization**
- Follow project pattern from dao/voting.rs and dao/roles.rs
- Use enum variants instead of byte string literals
- Rationale: Type-safe storage key management, consistent with existing codebase
