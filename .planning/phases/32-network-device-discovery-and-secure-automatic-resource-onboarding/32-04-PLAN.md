<objective>
Implement the acceptance gate (allowlist/blocklist with DAO governance), device fingerprinting service, and challenge-response authentication that form the middle of the discovery pipeline.

Purpose: After a device is discovered, it must be fingerprinted (identify type/manufacturer/capabilities), authenticated (prove identity via challenge-response), and checked against the acceptance gate (allowlist/blocklist/unknown handling). These three services transform raw discovery events into onboarding decisions.

Output: Three files covering the fingerprint-to-gate pipeline: fingerprint-service.ts (device probing), challenge-auth.ts (identity verification), acceptance-gate.ts (DAO-governed access decision).
</objective>

  <action>
**fingerprint-service.ts** — Device fingerprinting pipeline:

Create `FingerprintService` class:
1. `async fingerprint(event: DiscoveryEvent): Promise<DeviceFingerprint>` — Main entry point
2. Transport-specific fingerprinting strategies:
   - BLE: extract manufacturer from manufacturerData bytes (company ID lookup table for common vendors: Apple=0x004C, Samsung=0x0075, etc.), localName as displayName, serviceUuids as capabilities
   - WiFi/mDNS: parse service type from PTR name (e.g., _http._tcp → 'http'), extract model from TXT records if available
   - WiFi/SSDP: fetch UPnP device description XML from LOCATION header, extract friendlyName, manufacturer, modelName
   - USB: use vendorId/productId from serialport enumeration, manufacturer string, serialNumber as hardwareId
   - TAK/CoT: extract device type from CoT event type attribute (a-f-G for ground friendly, etc.), callsign from detail
3. `generateFingerprintHash(fingerprint: DeviceFingerprint): string` — SHA256 hash of canonical fingerprint for access list matching (use @noble/hashes/sha256)
4. Fingerprinting is async and can take time (UPnP description fetch). Design for pg-boss job execution per RESEARCH.md anti-pattern guidance: "Never fingerprint in the scan callback."

**challenge-auth.ts** — Challenge-response device authentication:

1. `generateChallenge(): { nonce: Buffer; timestamp: number; expiresAt: number }` — Generate 32-byte random nonce with 30-second expiry using crypto.randomBytes
2. `verifyChallenge(nonce: Buffer, response: Buffer, expectedPublicKey: string): Promise<ChallengeResult>` — Verify device signed the nonce
   - For DID-capable devices: ECDSA signature verification using @noble/curves/p256 or ed25519
   - Return ChallengeResult with success flag and devicePublicKey
3. `verifySimpleDevice(event: DiscoveryEvent, fingerprint: DeviceFingerprint): Promise<ChallengeResult>` — For simple devices (BLE peripherals, USB) that can't do crypto:
   - BLE: verify MAC address consistency + GATT service characteristic read
   - USB: verify vendorId/productId/serialNumber stability across reconnections
   - Return ChallengeResult with success=true and generated devicePublicKey (derived via HKDF from hardwareId, following resource-did.ts pattern)
4. Challenge expiry check: reject responses arriving after expiresAt timestamp
5. Failed challenges immediately return `{ success: false }` — caller handles quarantine
6. Use @noble/hashes for HKDF key derivation (consistent with existing resource-did.ts)

<task type="auto">
  <name>Task 2: Create acceptance gate with allowlist/blocklist and DAO integration</name>
  <files>backend/src/discovery/acceptance-gate.ts</files>
  <action>
Create `AcceptanceGate` class:

1. Constructor takes `discoveryStore` and optional `gateService` (for DAO gate creation)

2. `async evaluate(deviceId: string, fingerprint: DeviceFingerprint, scope: string): Promise<AcceptanceDecision>` — Main entry point:
   - Generate fingerprint hash via FingerprintService.generateFingerprintHash
   - Check against effective access list for the given scope (problem_set_id or 'global')
   - Check multiple match types in priority order:
     a. fingerprint_hash (most specific)
     b. mac (if rawIdentifier looks like MAC)
     c. vendor_id (from fingerprint.manufacturer)
     d. product_id (from fingerprint.model)
     e. cot_type (for TAK devices)
   - **Blocklist check first** — if ANY match type is blocked, return `{ decision: 'rejected' }` (blocklist takes precedence)
   - **Allowlist check second** — if any match type is allowed, return `{ decision: 'allowed' }`
   - **Unknown** — no match on either list, return `{ decision: 'unknown' }`

3. `AcceptanceDecision` type: `{ decision: 'allowed' | 'rejected' | 'unknown'; matchedEntry?: DeviceAccessEntry }`

4. `async createOnboardingGate(problemSetId: string, deviceId: string, fingerprint: DeviceFingerprint, ironclawAnalysis?: Record<string, unknown>): Promise<string>` — Creates a DAO decision gate for unknown device onboarding:
   - Extend GateType with 'device_onboard' and 'device_allowlist' values (add to gate-types.ts const)
   - Create gate via GateService.createGate with:
     - gate_type: 'device_onboard'
     - target_item_id: deviceId
     - target_item_type: 'device'
     - target_item_title: `Onboard: ${fingerprint.displayName || 'Unknown device'}`
     - enforcement: 'hard_block'
     - decision_context: { fingerprint, ironclawAnalysis } in the gate
   - Return gate ID

5. `async handleEmergencyDisconnect(deviceId: string, adminDid: string, reason: string): Promise<void>`:
   - Update device state to 'revoked'
   - Log the emergency disconnect with admin DID and reason
   - Create a post-hoc DAO gate for ratification (gate_type: 'device_onboard', enforcement: 'soft_warning')

6. Scope inheritance follows Phase 26 pattern: PS overrides ADD to global lists but cannot remove global blocklist entries.

7. Also modify `backend/src/gates/gate-types.ts` to add `device_onboard: 'device_onboard'` and `device_allowlist: 'device_allowlist'` to the GateType const object, and add default entries to GATE_DEFAULTS.
