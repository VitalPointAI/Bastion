  <name>Task 1: Create onboarding pipeline</name>
  <files>backend/src/discovery/onboarding-pipeline.ts</files>
  <action>
Create `OnboardingPipeline` class that chains the discovery pipeline stages:

1. Constructor takes dependencies: `discoveryStore`, `fingerprintService`, `acceptanceGate`, `resourceRegistry`, `messageBus` (dependency injection for testability)

2. `async processDiscoveryEvent(event: DiscoveryEvent, scope: string): Promise<OnboardingResult>`:
   - **Step 1: Deduplication** — Check discoveryStore.getDeviceByRawId(). If device exists:
     - If state is 'connected' or 'onboarding': update lastSeen, return early (already handled)
     - If state is 'disconnected': trigger RECONNECT flow (update state to 'connected', return success)
     - If state is 'rejected' or 'revoked': log attempt, return early (don't re-process)
     - If state is 'quarantined': log attempt, return early
   - **Step 2: Insert** — Create new discovered device record via discoveryStore.insertDiscoveredDevice
   - **Step 3: Fingerprint** — Update state to 'fingerprinting', call fingerprintService.fingerprint(event), store result
   - **Step 4: Authenticate** — Update state to 'authenticating', call appropriate auth based on transport:
     - For BLE/USB (simple): verifySimpleDevice(event, fingerprint)
     - For WiFi/TAK (network-capable): generateChallenge + verifyChallenge (or verifySimpleDevice if device doesn't respond to challenge)
     - On AUTH_FAIL: update state to 'quarantined' with reason 'auth_failed', return failure
   - **Step 5: Gate check** — Update state to 'gate_check', call acceptanceGate.evaluate()
     - 'allowed': proceed to onboarding, publish notification via messageBus
     - 'rejected': update state to 'rejected', publish security alert, return failure
     - 'unknown': update state to 'ironclaw_analysis', enqueue Ironclaw job (see below), return pending
   - **Step 6: Onboard** — Update state to 'onboarding':
     - Create resource DID via createResourceDID pattern
     - Register resource via resourceRegistry with trust tier 'observer' (per user decision: devices start as observer)
     - Update device record with deviceDid and resourceId
     - Update state to 'connected'
     - Publish onboarding success notification
     - Return OnboardingResult with success=true

3. `async processIronclawResult(deviceId: string, approved: boolean, analysis: Record<string, unknown>): Promise<void>`:
   - Called when Ironclaw analysis completes and DAO approves/rejects
   - If approved: update state from 'pending_dao' to 'onboarding', run Step 6
   - If rejected: update state to 'rejected'

4. Ironclaw job enqueueing: use pg-boss to enqueue `discovery.ironclaw_analysis` job with deviceId and fingerprint data. The Ironclaw service (Phase 30) will pick this up via its tool-bridge pattern.

5. All state transitions use discoveryStore.updateDeviceState which handles the XState lifecycle validation.

6. Error handling: any pipeline stage failure updates device state to 'quarantined' with error reason. Never leave a device in an intermediate state on error.

<task type="auto">
  <name>Task 2: Create discovery service singleton orchestrator</name>
  <files>backend/src/discovery/discovery-service.ts</files>
  <action>
Create `DiscoveryService` singleton class following ResourceRegistry pattern:

1. **Singleton pattern:** private constructor, `getDiscoveryService()` factory function

2. **Scanner management:**
   - Instantiate all 4 scanners: BLEScanner, WiFiScanner, USBScanner, TAKScanner
   - Store in a Map<TransportType, TransportScanner>
   - Track per-scanner config in a Map<TransportType, ScannerConfig> initialized from DEFAULT_SCAN_INTERVALS

3. **Interface restriction enforcement:**
   - Load disabled interfaces from admin config (key: 'discovery.disabled_interfaces')
   - Before starting any scanner, check if its transport type is disabled
   - This config is in PROTECTED_CONFIG_KEYS so Ironclaw cannot modify it
   - Admin-only API (separate from Ironclaw) can update interface restrictions

4. **`async initialize(): Promise<void>`:**
   - Initialize discoveryStore (ensure tables)
   - Instantiate OnboardingPipeline with all dependencies
   - Set up hot-load plugin watcher via watchForNewPlugins()
   - Wire scanner 'discovered' events to pipeline.processDiscoveryEvent()
   - Wire scanner 'lost' events to handle device disconnection (update state to 'disconnected')
   - Wire scanner 'error' events to error logging
   - Do NOT auto-start scanners — wait for explicit start()

5. **`start(scope?: string): void`** — Start all enabled scanners with their configs. Scope defaults to 'global'.
6. **`stop(): void`** — Stop all scanners.
7. **`pause(): void`** — Pause all scanners (operator pause/resume).
8. **`resume(): void`** — Resume all scanners.
9. **`setScannerConfig(transport: TransportType, config: Partial<ScannerConfig>): void`** — Update scanner config at runtime.
10. **`getStatus(): DiscoveryStatus`** — Return status of all scanners (running/paused/stopped/unavailable), device counts by state.

11. **`DiscoveryStatus` type:** { scanners: Record<TransportType, { available: boolean; running: boolean; paused: boolean; lastEvent?: number }>; deviceCounts: Record<DeviceState, number>; scope: string }

12. **Reconnection handling:** On scanner 'discovered' event, check if device was previously known (getDeviceByRawId). If previously disconnected, update state to 'connected' and re-establish any persistent connections based on trust tier.

13. **Connection persistence:** For participant/autonomous trust tier devices, maintain persistent connections (track in a Set). For observer devices, on-demand only.

14. **Event bus integration:** Publish discovery events to MessageBus on channels:
    - `discovery.device.${state}` — state change events
    - `discovery.scan.${transportType}` — scanner lifecycle events
