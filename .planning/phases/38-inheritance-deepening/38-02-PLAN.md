<task type="auto">
  <name>Task 1: Extend InheritanceService with notification, read-only enforcement, and interpretation ack methods</name>
  <files>backend/src/inheritance/inheritance-service.ts</files>
  <action>
Add new methods to the existing InheritanceService class:

**1. Read-only enforcement:**
- `enforceReadOnly(problemSetId: string, itemId: string): Promise<void>` — calls `inheritanceStore.isInheritedContent()`. If inherited, throws HTTP 403 error with message "Inherited content is read-only. Submit a modification request instead." This is the doctrinal constraint — inherited context cannot be modified at child level.

**2. Notification count aggregation:**
- `getNotificationCounts(problemSetId: string): Promise<{ pendingAcks: number; unreadChangelog: number; openRFIs: number; pendingFRAGOs: number }>` — aggregates counts from store methods. Used by frontend for tab badges and PS selector dot indicators. Returns combined count of: pending acknowledgments (significant only), unread changelog entries since last ack, open RFIs where this PS is targetProblemSetId, pending FRAGO drafts for child PSes.

**3. Interpretation acknowledgment loop:**
- `acknowledgeInterpretation(annotationId: string, parentProblemSetId: string, action: 'acknowledge' | 'clarify' | 'correct', comment: string | null, actedBy: string): Promise<InterpretationAcknowledgment>` — validates annotation exists and is of type 'interpretation' with visibility 'upward', creates interpretation ack record. If action is 'clarify', automatically creates an RFI with subtype 'clarification' linking back to the annotation. If action is 'correct', logs activity entry for child PS notification.

**4. Modification request handling:**
- `createModificationRequest(requestingPsId: string, targetPsId: string, targetItemId: string, targetItemType: string, subject: string, description: string, createdBy: string): Promise<InheritanceRFI>` — creates RFI with rfiSubtype='modification_request', initial message with the description, and logs activity for target PS.
- `resolveModificationRequest(rfiId: string, resolution: 'approved' | 'denied', comment: string, resolvedBy: string): Promise<void>` — updates RFI resolution, adds resolution message to thread, closes RFI, logs activity for requesting PS.

**5. Guidance request:**
- `createGuidanceRequest(requestingPsId: string, targetPsId: string, subject: string, situationDescription: string, createdBy: string): Promise<InheritanceRFI>` — creates RFI with rfiSubtype='guidance_request', initial message, activity log.

All methods follow existing service patterns: use `this.store` or `inheritanceStore` singleton, wrap in try/catch, log errors.

<task type="auto">
  <name>Task 2: Add API routes for notifications, interpretation acks, modification requests, and read-only enforcement middleware</name>
  <files>backend/src/api/inheritance.ts</files>
  <action>
Add new routes to the existing inheritance API router. Place new routes BEFORE the existing `/:id/` parametric routes to prevent Express route shadowing.

**New routes:**

1. `GET /:id/notification-counts` — calls `inheritanceService.getNotificationCounts(id)`, returns `{ pendingAcks, unreadChangelog, openRFIs, pendingFRAGOs, total }`. Used by frontend badges.

2. `POST /:id/annotations/:annotationId/acknowledge` — body: `{ action: 'acknowledge' | 'clarify' | 'correct', comment?: string }`. Validates action with zod. Calls `inheritanceService.acknowledgeInterpretation()`. Returns the created InterpretationAcknowledgment.

3. `GET /:id/annotations/:annotationId/acknowledgment` — returns existing InterpretationAcknowledgment for this annotation, or null.

4. `POST /:id/modification-requests` — body: `{ targetProblemSetId, targetItemId, targetItemType, subject, description }`. Calls `inheritanceService.createModificationRequest()`. Returns created RFI.

5. `PUT /:id/modification-requests/:rfiId/resolve` — body: `{ resolution: 'approved' | 'denied', comment }`. Calls `inheritanceService.resolveModificationRequest()`. Returns 200.

6. `POST /:id/guidance-requests` — body: `{ targetProblemSetId, subject, situationDescription }`. Calls `inheritanceService.createGuidanceRequest()`. Returns created RFI.

7. `GET /:id/rfis/by-subtype/:subtype` — returns RFIs filtered by subtype. Validate subtype is one of 'clarification', 'modification_request', 'guidance_request'.

**Read-only enforcement middleware:**
Add a check in the existing `POST /:id/annotations` route: if the annotation targets an item that is inherited content, allow it (annotations on inherited content are permitted). But do NOT add read-only checks to annotation routes — annotations are the intended way to interact with inherited content.

The read-only enforcement is for the API routes that directly modify inherited documents/items (those routes live in other modules). Add an exported middleware function `inheritedContentGuard` that other route files can import:
```typescript
export function inheritedContentGuard(req, res, next) {
  // Check if the targeted item is inherited; if so, block mutation with 403
}
```

All routes use zod for body validation, requireAuth middleware, and follow existing error handling patterns (try/catch with res.status(500).json).
