# Phase 25.3: AI Strategic Context & Knowledge Graph Integration - Research

**Researched:** 2026-03-06
**Domain:** AI context assembly, knowledge graph summarization, subscription cache materialization
**Confidence:** HIGH

## Summary

This phase wires strategic environment data (from subscriptions and containers) and container-scoped knowledge graph summaries into the AI agent context pipeline. The codebase already has all the foundational pieces: `ProblemSetSubscriptionStore` with an empty `problem_set_data_cache` table, `GraphBuilder` with RAFT extraction, centrality algorithms in `raft-tools.ts`, `assembleContextNode()` in `ai-role-graph.ts` as the injection point, and the container store from Phase 25.2. The work is primarily integration -- connecting these existing pieces through a new `StrategicContextService` and adding the cache materialization logic that was deferred when the subscription system was built.

The graph summary generation is the most technically interesting piece. The existing `fetchAdjacencyList()` and `computeEigenvectorCentrality()`/`computePageRank()` functions already compute centrality in-memory from Neo4j data. This phase needs to add container-scoped variants (filtering by `containerId` property on graph nodes) and package the results into a compact text summary suitable for injection into agent prompts. Temporal boosting based on the current scenario phase adds a ranking layer on top.

**Primary recommendation:** Build five discrete components in order: (1) cache materializer on `ProblemSetSubscriptionStore`, (2) `containerId` tagging on graph entities + container-scoped graph queries, (3) `getGraphSummary(containerId)` with centrality + TTL cache, (4) `StrategicContextService` that orchestrates cache + graph summaries into a token-budgeted bundle, (5) inject into `assembleContextNode()` + preview API/UI.

### Pattern 3: In-Memory TTL Cache for Graph Summaries
**What:** Simple Map-based cache with timestamp expiry for graph summaries.
**When to use:** Short-lived caches where data is expensive to compute but acceptable to be slightly stale.
**Example:**
```typescript
interface CacheEntry<T> {
  data: T;
  expiresAt: number;
}

class TTLCache<T> {
  private cache = new Map<string, CacheEntry<T>>();
  constructor(private ttlMs: number) {}

  get(key: string): T | undefined {
    const entry = this.cache.get(key);
    if (!entry || Date.now() > entry.expiresAt) {
      this.cache.delete(key);
      return undefined;
    }
    return entry.data;
  }

  set(key: string, data: T): void {
    this.cache.set(key, { data, expiresAt: Date.now() + this.ttlMs });
  }

  invalidate(key: string): void {
    this.cache.delete(key);
  }
}
```

### Anti-Patterns to Avoid
- **Fetching graph summaries during `runAgentsNode`:** Fetch once in `assembleContextNode`, not per-agent. All agents share the same strategic context.
- **Storing graph summaries in PostgreSQL cache:** Graph summaries change frequently (5-min TTL) and are lightweight. In-memory cache is correct; PostgreSQL adds unnecessary write load.
- **Full document text in agent context:** Always truncate. The 8000-token budget is for the ENTIRE strategic context, not per-document.
- **Blocking publisher requests on cache refresh:** Always use pg-boss async jobs for cross-problem-set cache invalidation.

## Common Pitfalls

### Pitfall 1: Missing problem_set_id on exercise_scenarios
**What goes wrong:** The `assembleContextNode` receives `scenarioId` but `StrategicContextService` needs `problemSetId`. The link is through `exercise_scenarios.problem_set_id` column.
**Why it happens:** The scenario-to-problem-set link was added later and some scenarios may not have it set.
**How to avoid:** Use `ScenarioStore.findByProblemSetId()` (reverse lookup exists), but for forward lookup, query `exercise_scenarios WHERE id = $scenarioId` and read `problem_set_id`. Handle null gracefully -- no strategic context available if no problem set linked.
**Warning signs:** Strategic context is always empty during exercises.

### Pitfall 2: Neo4j Unavailability Crashes Agent Pipeline
**What goes wrong:** Neo4j connection fails during `getGraphSummary()`, causing `assembleContextNode` to throw, which crashes the entire AI run.
**Why it happens:** Neo4j is an optional service that may not always be running.
**How to avoid:** Wrap all Neo4j calls in try/catch. When Neo4j is unavailable, degrade gracefully to doc-only context. Log warning but don't throw.
**Warning signs:** AI runs fail with "Neo4j connection refused" errors.

### Pitfall 3: Token Budget Overflow
**What goes wrong:** Strategic context exceeds 8000 tokens, overwhelming agent prompts and causing LLM token limit errors or degraded agent performance.
**Why it happens:** Multiple subscribed containers each contribute docs + graph summaries. Without strict budget enforcement, content grows unbounded.
**How to avoid:** Implement token budget as a hard cap in `StrategicContextService`. Build content in priority order (graph summary first, then extracted_data, then text_content), stop adding when budget exhausted. Include remaining budget in the context so agents know what was omitted.
**Warning signs:** Agent responses become generic or confused, ignoring strategic context.

### Pitfall 4: Cache Stampede on First Materialization
**What goes wrong:** Multiple concurrent requests all trigger cache materialization simultaneously because the cache is empty.
**Why it happens:** No lock/dedup on cache refresh jobs.
**How to avoid:** Use pg-boss's built-in `singletonKey` option on the job to ensure only one materialization runs per subscriber-publisher pair at a time.
**Warning signs:** Database CPU spikes, duplicate cache entries.

### Pitfall 5: containerId Not Added to Graph Entities
**What goes wrong:** Container-scoped graph queries return empty results even though entities exist.
**Why it happens:** Existing graph entities were created before `containerId` tagging was added. The `GraphBuilder.buildFromObjective()` passes `workspaceId` but not `containerId`.
**How to avoid:** Add `containerId` as an optional parameter to `GraphBuildOptions`. When auto-triggering from container document assignment, always pass the containerId. For existing entities, consider a migration or accept that pre-25.3 entities won't appear in container-scoped queries.
**Warning signs:** Graph summaries are empty for containers with documents that had graphs built before Phase 25.3.

### Pitfall 6: stale_at Column Missing from Existing Table
**What goes wrong:** The `problem_set_data_cache` table already exists but doesn't have the `stale_at` column that the stale-while-revalidate pattern needs.
**Why it happens:** Table was created in Phase 23 without this column.
**How to avoid:** Use `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` in the init function to add `stale_at` and any other new columns.
**Warning signs:** SQL errors on first cache write attempt.

## Code Examples

### Cache Materialization - Core Logic
```typescript
// Source: pattern derived from existing problem-set-subscription-store.ts
async materializeCache(subscriberProblemSetId: string): Promise<void> {
  const pool = getPool();

  // 1. Get approved subscriptions for this subscriber
  const subs = await this.listBySubscriber(subscriberProblemSetId);
  const approved = subs.filter(s => s.approvalStatus === 'approved');

  for (const sub of approved) {
    // 2. Fetch docs from publisher, filtered by subscription dataTypes
    const docs = await pool.query(`
      SELECT id, title, doc_type, text_content, extracted_data, updated_at
      FROM strategic_documents
      WHERE workspace_id = $1
        AND doc_type = ANY($2)
      ORDER BY updated_at DESC
    `, [sub.publisherProblemSetId, sub.dataTypes]);

    // 3. Compute source_version hash
    const { createHash } = await import('crypto');
    const versionHash = createHash('sha256')
      .update(docs.rows.map(d => d.updated_at.toISOString()).join('|'))
      .digest('hex')
      .slice(0, 16);

    // 4. Check if cache is current
    const existing = await pool.query(`
      SELECT source_version FROM problem_set_data_cache
      WHERE consumer_problem_set_id = $1 AND source_problem_set_id = $2
      LIMIT 1
    `, [subscriberProblemSetId, sub.publisherProblemSetId]);

    if (existing.rows[0]?.source_version === versionHash) continue;

    // 5. UPSERT cache entries
    for (const doc of docs.rows) {
      const payload = {
        title: doc.title,
        docType: doc.doc_type,
        extractedData: doc.extracted_data,
        textContent: (doc.text_content || '').slice(0, 2000),
      };

      await pool.query(`
        INSERT INTO problem_set_data_cache
          (id, consumer_problem_set_id, source_problem_set_id, data_type, payload, source_version, cached_at)
        VALUES ($1, $2, $3, $4, $5, $6, NOW())
        ON CONFLICT (consumer_problem_set_id, source_problem_set_id, data_type)
        DO UPDATE SET payload = $5, source_version = $6, cached_at = NOW(), stale_at = NULL
      `, [
        `PDC-${randomUUID()}`, subscriberProblemSetId,
        sub.publisherProblemSetId, doc.doc_type, JSON.stringify(payload), versionHash,
      ]);
    }
  }
}
```

### StrategicContextService - Assembly Flow
```typescript
// Source: new service following StoreContext pattern
export class StrategicContextService {
  private graphSummaryCache = new TTLCache<GraphSummary>(5 * 60 * 1000); // 5 min

  constructor(
    private subscriptionStore: ProblemSetSubscriptionStore,
    private containerStore: ContainerStore,
  ) {}

  async assembleContext(
    problemSetId: string,
    scenarioPhase?: string
  ): Promise<StrategicEnvironmentContext> {
    const TOKEN_BUDGET = 8000;
    let tokensUsed = 0;

    // 1. Get environment + containers for this problem set
    const env = await this.containerStore.getEnvironmentByProblemSet(problemSetId);
    const groups = await this.containerStore.getContainersGroupedByCategory(env.id);
    const containers = groups.flatMap(g => g.containers);

    // 2. Build graph summaries (priority 1)
    const graphSummaries: Record<string, GraphSummary> = {};
    for (const container of containers) {
      if (tokensUsed >= TOKEN_BUDGET) break;
      const summary = await this.getGraphSummary(container.id, scenarioPhase);
      if (summary) {
        const tokens = Math.ceil(JSON.stringify(summary).length / 4);
        if (tokensUsed + tokens <= TOKEN_BUDGET) {
          graphSummaries[container.name] = summary;
          tokensUsed += tokens;
        }
      }
    }

    // 3. Get cached docs from subscriptions (priority 2: extracted_data, then text)
    const cachedDocs = await this.getCachedDocSummaries(problemSetId, TOKEN_BUDGET - tokensUsed);

    return {
      graphSummaries,
      documentSummaries: cachedDocs,
      tokensUsed: tokensUsed + cachedDocs.tokensUsed,
      tokenBudget: TOKEN_BUDGET,
    };
  }
}
```

## Open Questions

1. **Container-scoped graph entities: array vs single property**
   - What we know: Existing entities use `workspaceId` as a single string property. Documents can belong to multiple containers.
   - What's unclear: Should `containerId` be a single string or an array (like `sourceDocumentIds`)?
   - Recommendation: Use `containerIds` as a string array since a document (and its extracted entities) can belong to multiple containers. This matches the `sourceDocumentIds` pattern already on entities.

2. **Existing graph entities without containerId**
   - What we know: All current graph entities have `workspaceId` but no `containerId`.
   - What's unclear: Should we backfill `containerId` on existing entities based on their `sourceDocumentIds` and container-document assignments?
   - Recommendation: Add `containerId` going forward only. Backfilling can be a separate task if needed. Container-scoped graph queries will only return entities created/updated after Phase 25.3.

3. **Cache table schema modification approach**
   - What we know: `problem_set_data_cache` exists with a fixed schema. Need to add `stale_at` column and potentially modify the UNIQUE constraint (currently per data_type, but we may want per-document granularity).
   - What's unclear: Whether the current UNIQUE(consumer, source, data_type) constraint is sufficient or if we need per-document cache entries.
   - Recommendation: Keep the current constraint for now. Each subscription creates one cache entry per `data_type` from the publisher. The `payload` JSONB can hold an array of document summaries per type. Add `stale_at TIMESTAMPTZ` column via `ALTER TABLE ADD COLUMN IF NOT EXISTS`.
