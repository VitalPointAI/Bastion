# Phase 25.3: AI Strategic Context & Knowledge Graph Integration - Context

**Gathered:** 2026-03-06
**Status:** Ready for planning
**Depends on:** Phase 25.2 (containers provide the organizational structure for documents and graph scoping)

<domain>
## Phase Boundary

Wire subscribed strategic environment data and container-scoped knowledge graphs into AI agent context so that AI agents and teams have access to all strategic documents and graph-derived knowledge when interacting with users in a problem set. Does NOT include tool-bound graph queries for exercise agents (future), full strategic environment inheritance (Phase 26), or new AI agent types (Phase 29).

</domain>

<decisions>
## Implementation Decisions

### Subscription Cache Materializer
- Add `materializeCache()` method to `ProblemSetSubscriptionStore` that queries approved subscriptions, fetches strategic docs from publisher problem sets (and containers after 25.2), filters by subscription `dataTypes`, and UPSERTs into `problem_set_data_cache`
- Cache uses `source_version` (hash of doc `updated_at` timestamps) to skip re-materialization when source hasn't changed
- Materialization triggered on: subscription approved, new doc added to subscribed container, on-demand refresh via API
- Truncate `text_content` to ~2000 chars per doc in cache; prioritize `extracted_data` (structured) over raw text

### Container-Scoped Knowledge Graph Construction
- When documents are added/updated in a strategic container, auto-trigger RAFT extraction (actors, relationships, tensions) into Neo4j
- Tag all graph entities with `containerId` alongside existing `workspaceId` for container-level graph queries
- Leverage existing `graph-builder.ts` pipeline and RAFT extraction prompts -- no new LLM prompts needed
- Auto-trigger mechanism: use 25.2's container-level agent assignment (standing orders) to assign RAFT Extraction Agent to containers
- Add `getGraphSummary(containerId)` query that runs centrality analysis + key actor profiles for a container's sub-graph

### AI Context Assembly Integration
- Create `StrategicContextService` that orchestrates: problemSetId -> approved subscriptions -> cached docs + graph summaries -> bundled context
- Extend `assembleContextNode()` in `ai-role-graph.ts` to call `StrategicContextService` via the scenario's linked `problem_set_id`
- Inject strategic context into `sharedContext` under key `strategicEnvironment` containing both document summaries and graph summary
- Extend `contextSummary` in `runAgentsNode()` to include the strategic environment bundle

### Context Size Management
- Cap total strategic context at ~8000 tokens to avoid overwhelming agent prompts
- Prioritize: graph summary (most structured) > extracted_data > truncated text_content
- When multiple containers are subscribed, allocate token budget proportionally by document count
- Future enhancement: agents can request full document content via tool calls (not in this phase)

### Cache Invalidation
- When a strategic document is created/updated in a publisher problem set -> mark cache stale for all subscriber problem sets
- When a subscription is approved -> trigger initial cache population
- Add `stale_at` column or TTL check to `problem_set_data_cache`
- Stale cache served while refresh runs in background (stale-while-revalidate pattern)

### Claude's Discretion
- Exact graph summary format and serialization
- Token counting/estimation approach for context budget
- Whether to use pg-boss job for async cache materialization or inline
- Error handling when Neo4j is unavailable (degrade to doc-only context)
- Exact Cypher queries for container-scoped graph summaries

</decisions>

<specifics>
## Specific Ideas

- Graph summary should include: top actors by centrality, key relationships (alliances/conflicts), active tensions with intensity, and community clusters -- this gives agents a "strategic picture at a glance"
- The `StrategicContextService` should be usable both by the exercise AI pipeline AND by future per-tab AI assistants (Phase 29)
- Cache refresh could be a pg-boss scheduled job (e.g., every 5 minutes) rather than purely event-driven, as a fallback
- Consider exposing a "strategic context preview" endpoint for the frontend so users can see what their AI agents will know

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ProblemSetSubscriptionStore` (`problem-set-subscription-store.ts`): subscription CRUD, `problem_set_data_cache` table already exists but is never written to
- `AIContextStore` (`exercise/ai-context-store.ts`): additive JSONB merge with pg_notify -- pattern for cross-role context sharing
- `graph-builder.ts`: LLM-powered RAFT extraction from documents (actors, relationships, tensions)
- `actor-store.ts`, `relationship-store.ts`, `tension-store.ts`: Neo4j CRUD for all graph entities
- `raft-extraction-agent.ts`: existing agent with tools for graph construction
- `raft-reasoning-agent.ts`: existing agent with `query_graph`, `run_graph_algorithm`, `get_actor_profile` tools
- `graph.ts` API: `centrality-comparison` endpoint runs eigenvector + PageRank analysis
- `scenario-store.ts`: `findByProblemSetId()` links scenarios to problem sets
- `assembleContextNode()` and `runAgentsNode()` in `ai-role-graph.ts`: the injection points for agent context

### Established Patterns
- `StoreContext` type in `ai-role-graph.ts`: pattern for passing stores through the LangGraph pipeline
- `getSharedBoss()` singleton in `database.ts`: pg-boss for async job scheduling
- `workspaceId` tagging on all Neo4j nodes: existing multi-tenant isolation pattern
- `sourceDocumentIds` on graph entities: provenance tracking back to source documents

### Integration Points
- `assembleContextNode()` (ai-role-graph.ts:97-127): primary injection point for strategic context
- `runAgentsNode()` (ai-role-graph.ts:133-169): where context becomes part of agent prompts
- `StoreContext` type (ai-role-graph.ts:84-89): needs `StrategicContextService` added
- `initAIWorkspace()` (exercise.ts:134-139): where new service gets initialized
- `problem_set_data_cache` table (subscription-store.ts:44-57): existing but empty cache table
- `POST /graph/build/:documentId` (graph.ts): existing graph construction trigger

</code_context>
