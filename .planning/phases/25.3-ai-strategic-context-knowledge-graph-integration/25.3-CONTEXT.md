# Phase 25.3: AI Strategic Context & Knowledge Graph Integration - Context

**Gathered:** 2026-03-06
**Updated:** 2026-03-06
**Status:** Ready for planning
**Depends on:** Phase 25.2 (containers provide the organizational structure for documents and graph scoping)

<domain>
## Phase Boundary

Wire subscribed strategic environment data and container-scoped knowledge graphs into AI agent context so that AI agents and teams have access to all strategic documents and graph-derived knowledge when interacting with users in a problem set. Includes a strategic context preview UI so users can inspect what their AI agents know. Does NOT include tool-bound graph queries for exercise agents (future), full strategic environment inheritance (Phase 26), or new AI agent types (Phase 29).

</domain>

<decisions>
## Implementation Decisions

### Subscription Cache Materializer
- Add `materializeCache()` method to `ProblemSetSubscriptionStore` that queries approved subscriptions, fetches strategic docs from publisher problem sets (and containers after 25.2), filters by subscription `dataTypes` at cache time (only store matching doc types), and UPSERTs into `problem_set_data_cache`
- Cache uses `source_version` (hash of doc `updated_at` timestamps) to skip re-materialization when source hasn't changed
- Materialization triggered event-driven only: subscription approved, new doc added to subscribed container, on-demand refresh via API. No scheduled fallback.
- Truncate `text_content` to ~2000 chars per doc in cache; prioritize `extracted_data` (structured) over raw text
- Cache docs only -- graph summaries fetched live from Neo4j at context assembly time
- Cache invalidation: when source docs change in publisher problem set, queue async cache refresh via pg-boss (non-blocking for publisher). Add `stale_at` column with stale-while-revalidate pattern.

### Container-Scoped Knowledge Graph Construction
- Auto-trigger RAFT extraction (actors, relationships, tensions) when documents are added/updated in a strategic container -- fire-and-forget, no user confirmation needed
- Leverage existing `graph-builder.ts` pipeline and RAFT extraction prompts -- no new LLM prompts needed
- Auto-trigger mechanism: use 25.2's container-level agent assignment (standing orders) to assign RAFT Extraction Agent to containers
- Tag all graph entities with `containerId` AND existing `workspaceId` (both tags) for container-level AND workspace-level queries
- Add `getGraphSummary(containerId)` query that runs centrality analysis + key actor profiles for a container's sub-graph
- Cache graph summary results with short TTL (~5 min), invalidate when graph changes

### Graph Summary Content
- Graph summary includes: top actors by centrality, key relationships (alliances/conflicts), active tensions with intensity, community clusters, AND temporal relevance to current scenario phase
- Actors/relationships relevant to current scenario phase get boosted priority within the graph summary
- This gives agents a "strategic picture at a glance" with emphasis on what matters right now

### AI Context Assembly Integration
- Create `StrategicContextService` as a singleton, initialized at startup, passed via `StoreContext` -- consistent with existing store patterns
- Orchestrates: problemSetId -> approved subscriptions -> cached docs + live graph summaries -> bundled context
- Extend `assembleContextNode()` in `ai-role-graph.ts` to call `StrategicContextService` via the scenario's linked `problem_set_id`
- Inject strategic context into `sharedContext` under key `strategicEnvironment` containing both document summaries and graph summary
- All agents on a team see the same strategic context (no role-based filtering -- agents self-select from their role prompt)
- Extend `contextSummary` in `runAgentsNode()` to include the strategic environment bundle
- Service designed to be reusable by both exercise AI pipeline AND future per-tab AI assistants (Phase 29)

### Strategic Context Preview
- Include in this phase: API endpoint + frontend UI panel showing the assembled strategic context
- Users can inspect what their AI agents will know about the strategic environment
- Preview UI placement: Claude's discretion based on existing UI layout and navigation patterns

### Context Size Management
- Cap total strategic context at ~8000 tokens to avoid overwhelming agent prompts
- Token counting via character estimation (~4 chars per token) -- no tiktoken dependency
- Prioritization order: graph summary (with temporal boosting) > extracted_data > truncated text_content
- When multiple containers are subscribed, allocate token budget weighted by relevance -- containers with graph entities relevant to current scenario phase get larger share
- Future enhancement: agents can request full document content via tool calls (not in this phase)

### Claude's Discretion
- Exact graph summary format and serialization
- Strategic context preview UI placement (problem set settings vs AI panel)
- Whether to use pg-boss job for async cache materialization or inline triggers
- Error handling when Neo4j is unavailable (degrade to doc-only context)
- Exact Cypher queries for container-scoped graph summaries
- Graph summary TTL cache implementation details

</decisions>

<specifics>
## Specific Ideas

- Graph summary should give agents a "strategic picture at a glance" with temporal awareness of the current scenario phase
- The `StrategicContextService` should be usable both by the exercise AI pipeline AND by future per-tab AI assistants (Phase 29)
- Strategic context preview lets users verify their AI agents have the right information before running exercises
- Temporal boosting: actors/relationships active or changing in the current scenario phase rank higher in the graph summary

## Existing Code Insights

### Reusable Assets
- `ProblemSetSubscriptionStore` (`problem-set-subscription-store.ts`): subscription CRUD, `problem_set_data_cache` table already exists but is never written to
- `AIContextStore` (`exercise/ai-context-store.ts`): additive JSONB merge with pg_notify -- pattern for cross-role context sharing
- `graph-builder.ts`: LLM-powered RAFT extraction from documents (actors, relationships, tensions)
- `actor-store.ts`, `relationship-store.ts`, `tension-store.ts`: Neo4j CRUD for all graph entities
- `raft-extraction-agent.ts`: existing agent with tools for graph construction
- `raft-reasoning-agent.ts`: existing agent with `query_graph`, `run_graph_algorithm`, `get_actor_profile` tools
- `graph.ts` API: `centrality-comparison` endpoint runs eigenvector + PageRank analysis
- `scenario-store.ts`: `findByProblemSetId()` links scenarios to problem sets
- `assembleContextNode()` and `runAgentsNode()` in `ai-role-graph.ts`: the injection points for agent context
- Container store (`strategic/containers/store.ts`): new from Phase 25.2

### Established Patterns
- `StoreContext` type in `ai-role-graph.ts`: pattern for passing stores through the LangGraph pipeline
- `getSharedBoss()` singleton in `database.ts`: pg-boss for async job scheduling
- `workspaceId` tagging on all Neo4j nodes: existing multi-tenant isolation pattern
- `sourceDocumentIds` on graph entities: provenance tracking back to source documents
- `containerId` tagging on container entities (Phase 25.2): container-level scoping pattern

### Integration Points
- `assembleContextNode()` (ai-role-graph.ts:97-127): primary injection point for strategic context
- `runAgentsNode()` (ai-role-graph.ts:133-169): where context becomes part of agent prompts
- `StoreContext` type (ai-role-graph.ts:84-89): needs `StrategicContextService` added
- `initAIWorkspace()` (exercise.ts:134-139): where new service gets initialized
- `problem_set_data_cache` table (subscription-store.ts:44-57): existing but empty cache table
- `POST /graph/build/:documentId` (graph.ts): existing graph construction trigger
