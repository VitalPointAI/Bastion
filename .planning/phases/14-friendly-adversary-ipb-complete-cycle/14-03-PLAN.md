  <files>backend/src/exercise/ipb-service.ts</files>
  <action>
Create `backend/src/exercise/ipb-service.ts` with an `IPBService` class that assembles IPB assessments from extracted scenario documents.

Constructor takes: `pool: Pool`, `ipbStore: IPBStore`, `documentStore: ScenarioDocumentStore`, and LLM provider config.

**Core method:** `assembleIPB(scenarioId: string, team: 'blue' | 'red', perspective: 'own' | 'enemy_assessment', exercisePhase: string, visibleTeams: string[]): Promise<IPBAssessment>`

The method:

1. **Gather source documents** — Query `documentStore.findByScenarioAndPhase(scenarioId, exercisePhase, visibleTeams)` to get all documents visible to the requesting team for that phase.

2. **Filter by perspective:**
   - `perspective: 'own'` — Use documents where `team === requestingTeam`. For Blue's own view: Blue ALERTORDs, Blue SITREPs, Blue Campaign Plans. For Red's own view: Red ALERTORDs, Red SITREPs, Red Campaign Plans.
   - `perspective: 'enemy_assessment'` — Use documents where `team === requestingTeam` (because the assessment of the enemy comes from own intelligence, NOT from looking at the enemy's actual documents). The LLM synthesizes what this team believes about the other side based on available intelligence.

3. **Build IPB components using LLM:**
   Send the extracted data from gathered documents to the LLM with a structured extraction prompt requesting:
   - `areaOfOperations`: GeoJSON Polygon bounding the operational area (for Indo-Pacific: approximate lat/lng bounds for the Western Pacific theater)
   - `terrainAnalysis`: OAKOC structure (Observation & fields of fire, Avenues of approach, Key terrain, Obstacles, Cover & concealment) — use the structure from `mdmp-ipb-analysis.ts` RAFT template as reference
   - `threatAssessment`: Force composition, capabilities, likely COAs, vulnerabilities
   - `civilConsiderations`: ASCOPE factors (Areas, Structures, Capabilities, Organizations, People, Events)
   - `namedAreasOfInterest`: Array of {name, purpose, geometry (GeoJSON Point or Polygon), triggers}
   - `forceDispositions`: Array of force units with {unitName, echelon, sidc (MIL-STD-2525D), location ({lat, lng}), strength, equipment}

4. **Generate overlay layers** — Convert the IPB components into `IPBLayer[]` for ValidityMap rendering:
   - Force disposition units → type='unit', layerType='forces', geometry=Point, sidc from extraction
   - Key terrain → type='area', layerType='key_terrain', geometry=Polygon
   - Avenues of approach → type='line', layerType='avenue_of_approach', geometry=LineString
   - NAIs → type='point' or 'area', layerType='nai', geometry from NAI
   - For SIDC codes: use affiliation character in position 2 — 'F' for friendly (blue), 'H' for hostile (red from blue's perspective), 'N' for neutral. Follow MIL-STD-2525D patterns already used in `symbol-renderer.ts`.

5. **Store the assessment** via `ipbStore.create()` with all assembled fields, version=1.

**Update method:** `updateIPBFromSITREP(assessmentId: string, sitrepDocId: string, visibleTeams: string[]): Promise<IPBAssessment>`
- Load existing IPB assessment
- Load the new SITREP document's extracted data
- Use LLM to compare SITREP content against current assessment and identify deltas
- Create a new version via `ipbStore.createNewVersion()` with updated fields
- Return the delta summary in the assessment's metadata for impact flagging

**Helper:** `generateDeltaSummary(oldAssessment: IPBAssessment, newAssessment: IPBAssessment): DeltaSummary`
- Field-level comparison of force dispositions, threat assessment, named areas
- Returns: `{ changedFields: string[], addedUnits: string[], removedUnits: string[], significanceLevel: 'minor' | 'major' | 'critical' }`
- Significance: any change to force disposition or threat COAs = 'major'; change to unit strength/equipment only = 'minor'; new hostile unit or removed friendly unit = 'critical'

Default geographic coordinates for the exercise theater (Claude's discretion per CONTEXT.md):
- Western Pacific theater center: lat=20, lng=125
- Taiwan Strait focus area: lat=24.5, lng=120
- South China Sea: lat=15, lng=115

<task type="auto">
  <name>Task 2: COA Scoring Service — Doctrinal + Wargame Combined Scoring</name>
  <files>backend/src/exercise/coa-scoring-service.ts</files>
  <action>
Create `backend/src/exercise/coa-scoring-service.ts` with a `COAScoringService` class.

Constructor takes: `pool: Pool`, `coaStore: COAStore`, and LLM provider config.

**Core method:** `scoreCOA(coaId: string, visibleTeams: string[]): Promise<ExerciseCOAScore>`

1. Load the COA from `coaStore.findById(coaId, visibleTeams)`
2. Send COA description + scheme to LLM with structured extraction requesting scores for 5 doctrinal criteria:
   - **Feasibility** (0-100): Can the force accomplish the mission with available resources?
   - **Acceptability** (0-100): Are the expected outcomes worth the costs/risks?
   - **Suitability** (0-100): Does the COA accomplish the mission and comply with guidance?
   - **Distinguishability** (0-100): Is this COA significantly different from others?
   - **Completeness** (0-100): Does it address all aspects of the operational problem?
   Each criterion returns { score, rationale }.
3. If wargame evidence exists on the COA (`wargameEvidence` field), augment each criterion's rationale with wargame evidence string:
   - Feasibility ← wargame outcomes showing resource adequacy
   - Acceptability ← wargame casualty/loss projections
   - Suitability ← wargame mission accomplishment rate
   Update the `wargameEvidence` field on each criterion score.
4. Calculate combinedScore using equal weights (20% each) — this is Claude's discretion per CONTEXT.md. Formula: `(feasibility.score + acceptability.score + suitability.score + distinguishability.score + completeness.score) / 5`
5. Generate AI narrative synthesis using LLM — a 2-3 paragraph summary of the COA's strengths, weaknesses, and key trade-offs. This is the staff-editable narrative that goes to the commander.
6. Store scores via `coaStore.updateScores(coaId, scores)`
7. Return the complete `ExerciseCOAScore`

**Wargame integration method:** `integrateWargameResults(coaId: string, wargameSessionId: string, outcomes: Record<string, unknown>, visibleTeams: string[]): Promise<void>`
- Store wargame evidence on the COA via `coaStore.updateWargameEvidence(coaId, { sessionId, outcomes })`
- Re-score the COA with wargame evidence included (call `scoreCOA` again)
- Update the narrative to reflect wargaming insights

**Compare method:** `compareCOAs(coaIds: string[], visibleTeams: string[]): Promise<COAComparisonResult>`
- Load all COAs
- Build comparison matrix: rows = criteria, columns = COAs, cells = scores
- Identify: highest-scoring COA overall, best/worst per criterion
- Generate LLM comparison narrative: "COA 1 scores highest on feasibility because...; COA 2 offers better acceptability because..."
- Return: `{ matrix, rankings, narrative, recommendation }`

**COAComparisonResult type:**
```typescript
{
  matrix: Array<{ criterion: string; scores: Array<{ coaId: string; coaName: string; score: number }> }>;
  rankings: Array<{ coaId: string; coaName: string; combinedScore: number; rank: number }>;
  narrative: string;  // Staff-editable
  recommendation: string;  // AI staff recommendation
}
```

**Commander decision method:** `recordCommanderDecision(coaId: string, decision: string, notes: string): Promise<{hash: string}>`
- Call `coaStore.recordDecision(coaId, decision, notes)`
- Compute SHA-256 hash of the decision record: `JSON.stringify({ coaId, decision, notes, timestamp })`
- Store hash via `coaStore.updateDecisionHash(coaId, hash)`
- Write to outbox table for NEAR blockchain anchoring (existing pattern from `blockchain-sync.ts`):
  `INSERT INTO outbox (aggregate_id, payload) VALUES ($1, $2)` with `{ type: 'commander_decision', hash, coaId }`
- Return the hash
