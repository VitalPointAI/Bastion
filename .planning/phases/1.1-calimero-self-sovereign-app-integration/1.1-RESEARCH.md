# Phase 1.1: Calimero Self-Sovereign App Integration - Research

**Researched:** 2026-01-20
**Domain:** Self-sovereign applications, DAO compartmentalization, Privy replacement
**Confidence:** HIGH

<research_summary>
## Summary

Researched the Calimero Network ecosystem for replacing Privy authentication with self-sovereign NEAR account management and implementing DAO compartmentalization. The standard approach uses Calimero's "context" model for private peer-to-peer networks, NEAR implicit accounts for Web2-style onboarding, and NEAR Chain Signatures MPC for key recovery.

Key finding: Calimero represents a fundamental shift from "managed authentication service" (Privy) to "self-sovereign application layer" where users own their data and control access. Instead of a centralized auth provider, each DAO becomes a private "context" with CRDT-based state, end-to-end encryption, and NEAR blockchain settlement for critical decisions.

The migration path involves: (1) replacing `@privy-io/react-auth` with `@calimero-network/calimero-client` + `@near-wallet-selector`, (2) restructuring DAO storage from on-chain contracts to Calimero contexts with NEAR settlement, and (3) updating identity management to use hierarchical key delegation.

**Primary recommendation:** Adopt Calimero SDK for DAO compartmentalization with NEAR FastAuth (Auth0 + MPC) for Web2-style onboarding, keeping NEAR blockchain for critical decision audit trails.
</research_summary>

## Architecture Patterns

### Recommended Project Structure
```
src/
├── calimero/            # Calimero integration
│   ├── config.ts        # Node URL, Application ID configuration
│   ├── context.tsx      # Calimero context provider
│   └── client.ts        # RPC and subscription clients
├── auth/                # Authentication
│   ├── WalletAuth.tsx   # NEAR wallet connection
│   ├── SessionManager.ts # JWT token management
│   └── KeyManager.ts    # Hierarchical key delegation
├── dao/                 # DAO contexts
│   ├── DAOContext.ts    # Calimero context per DAO
│   └── Settlement.ts    # NEAR blockchain settlement
└── lib/
    ├── crdt/            # CRDT state helpers
    └── encryption/      # E2E encryption utilities
```

### Pattern 1: Calimero Context as Private DAO
**What:** Each DAO becomes a Calimero "context" - a private P2P network with scoped state
**When to use:** Any private multi-party coordination (DAOs, teams, coalitions)
**Example:**
```typescript
// Source: Calimero docs - context model
// A context is an application-specific network enabling direct communication
// Participants sync only with each other, not the entire network

interface DAOContext {
  contextId: string;           // Unique context identifier
  applicationId: string;       // WASM app running in context
  participants: string[];      // DID-based member list
  crdtState: UnorderedMap;     // CRDT-backed DAO state
  settlementContract: string;  // NEAR contract for finality
}

// Context isolation: Each DAO's state is private to members
// No global consensus required - CRDT handles conflict resolution
```

### Pattern 2: Hierarchical Identity with Key Delegation
**What:** Root keys delegate client keys per device, integrating with NEAR wallets
**When to use:** Multi-device access, recoverable accounts
**Example:**
```typescript
// Source: Calimero core README
// Root keys delegate client keys per device

interface HierarchicalIdentity {
  rootKey: {
    did: string;              // did:near:account.near
    publicKey: string;        // Root Ed25519 public key
  };
  clientKeys: {
    deviceId: string;         // Unique device identifier
    publicKey: string;        // Device-specific key
    delegatedBy: string;      // Root key DID
    permissions: string[];    // Scoped permissions
  }[];
}

// Key recovery via NEAR Chain Signatures MPC
// 8-node MPC network - no single entity can reconstruct key
```

### Pattern 3: NEAR Settlement for Critical Decisions
**What:** Use Calimero for operations, NEAR blockchain for finality
**When to use:** Audit trails, strike authorizations, coalition approvals
**Example:**
```typescript
// Calimero for fast P2P operations
// NEAR blockchain for critical decision settlement

async function settleDecision(
  contextId: string,
  proposalId: string,
  decision: 'approved' | 'rejected'
) {
  // Step 1: Record decision in Calimero context (fast, private)
  await calimeroClient.execute({
    contextId,
    method: 'record_decision',
    args: { proposalId, decision, timestamp: Date.now() }
  });

  // Step 2: Settle on NEAR blockchain (auditable, permanent)
  await nearContract.functionCall({
    contractId: 'dao.near',
    methodName: 'settle_decision',
    args: {
      context_id: contextId,
      proposal_id: proposalId,
      decision,
      proof: await calimeroClient.getProof(proposalId)
    }
  });
}
```

### Pattern 4: Web2-Style Onboarding with FastAuth
**What:** Email signup with passkey biometrics, MPC-backed recovery
**When to use:** User-facing applications requiring Web2 UX
**Example:**
```typescript
// Source: NEAR FastAuth docs (being updated to Auth0 + MPC)
// Users sign up with email, authenticate with biometrics
// No seed phrases, no wallet downloads

// Current flow (deprecated but functional):
// 1. User enters email
// 2. Creates passkey (FaceID/fingerprint)
// 3. NEAR account created via meta-transaction (gasless)
// 4. MPC recovery linked to email

// New flow (in development):
// 1. Auth0 handles email/social login
// 2. MPC key derivation from Auth0 identity
// 3. Same user experience, improved infrastructure
```

### Anti-Patterns to Avoid
- **Storing private keys in backend:** Calimero's model is self-sovereign; keys stay on user devices
- **Global state for private data:** Use Calimero contexts for DAO-scoped isolation
- **Polling for updates:** Use Calimero's WebSocket subscriptions for real-time sync
- **Custom consensus for P2P:** CRDTs handle conflict resolution automatically
</architecture_patterns>

<dont_hand_roll>
## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| P2P data sync | Custom sync protocol | Calimero CRDT | CRDTs handle offline-first, merge conflicts automatically |
| Key management | Backend key storage | NEAR Chain Signatures | MPC network ensures no single point of compromise |
| DAO privacy | Custom encryption layer | Calimero contexts | End-to-end encryption built-in with peer verification |
| Wallet connection | Custom wallet UI | @near-wallet-selector | Handles 10+ NEAR wallets with consistent API |
| Web2 auth flow | Custom email/password | FastAuth / Auth0 | Passkey security, MPC recovery, gasless onboarding |
| Real-time updates | WebSocket implementation | Calimero SubscriptionsClient | Built-in SSE/WebSocket with reconnection handling |
| State verification | Custom proof system | Calimero + NEAR settlement | Cross-chain proof verification for multiple blockchains |

**Key insight:** Calimero is an application layer, not a blockchain. It uses CRDTs instead of consensus, enabling "practically instantaneous" execution while still allowing NEAR blockchain settlement for auditable finality. Don't try to replicate this architecture with custom WebSocket sync or hand-rolled encryption.
</dont_hand_roll>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Treating Calimero as a Blockchain
**What goes wrong:** Attempting global consensus patterns or expecting all nodes to have same state
**Why it happens:** Mental model from traditional blockchain development
**How to avoid:** Understand "eventual consistency" model - each peer drives local state, network reconciles
**Warning signs:** Waiting for "confirmations," trying to enforce global ordering

### Pitfall 2: Centralized Authentication Mindset
**What goes wrong:** Building backend services that manage user keys or sessions
**Why it happens:** Privy's managed model vs Calimero's self-sovereign model
**How to avoid:** Keys stay on user devices; backend only sees signed messages
**Warning signs:** Backend storing private keys, centralized session database

### Pitfall 3: Ignoring Context Isolation
**What goes wrong:** Sharing state across contexts, leaking DAO data
**Why it happens:** Not understanding context boundaries
**How to avoid:** Each DAO context is isolated; use explicit cross-context communication
**Warning signs:** Global state stores, single context for multiple DAOs

### Pitfall 4: FastAuth Deprecation
**What goes wrong:** Building on current FastAuth SDK when it's being replaced
**Why it happens:** Documentation shows deprecated version
**How to avoid:** Watch for Auth0 + MPC version; current implementation works but will change
**Warning signs:** Using Firebase-based FastAuth config when Auth0 is available

### Pitfall 5: Over-Settlement
**What goes wrong:** Settling every operation on NEAR blockchain
**Why it happens:** Blockchain-first thinking vs Calimero's off-chain model
**How to avoid:** Only settle critical decisions (strike auth, final votes); use Calimero for operations
**Warning signs:** High gas costs, slow operations, blockchain as database
</common_pitfalls>

## Code Examples

Verified patterns from official sources:

### Calimero Client Setup
```typescript
// Source: @calimero-network/calimero-client npm docs
import {
  setAppEndpointKey,
  setApplicationId,
  getAccessToken,
  ClientLogin,
  SetupModal
} from '@calimero-network/calimero-client';

// Configuration (environment variables recommended)
setAppEndpointKey(process.env.CALIMERO_NODE_URL);
setApplicationId(process.env.CALIMERO_APP_ID);

// Authentication wrapper at app root
function App() {
  return (
    <CalimeroAuthProvider>
      <SetupModal successRoute={() => window.location.href = '/dashboard'} />
      <ClientLogin sucessRedirect={() => console.log('Logged in')} />
      <MainContent />
    </CalimeroAuthProvider>
  );
}
```

### RPC and Subscription Clients
```typescript
// Source: calimero-client-js GitHub README
import { JsonRpcClient, SubscriptionsClient } from '@calimero-network/calimero-client';

// RPC for queries and mutations
const rpcClient = new JsonRpcClient(nodeUrl, '/jsonrpc');
const response = await rpcClient.query({
  contextId,
  method: 'get_dao_state',
  args: {}
});

// Subscriptions for real-time updates
const subsClient = new SubscriptionsClient(nodeUrl);
subsClient.subscribe({
  contextId,
  events: ['proposal_created', 'vote_cast'],
  callback: (event) => {
    console.log('Event received:', event);
    updateUI(event);
  }
});
```

### NEAR Wallet Selector Integration
```typescript
// Source: NEAR wallet-selector docs
import { setupWalletSelector } from '@near-wallet-selector/core';
import { setupModal } from '@near-wallet-selector/modal-ui';

const selector = await setupWalletSelector({

    setupMyNearWallet(),

  description: 'Connect to BASTION'

```

### Chain Signatures MPC Integration
```typescript
// Source: NEAR Chain Signatures docs
// Sign transaction via MPC network (no private key exposure)

const signatureResult = await nearAccount.functionCall({
  contractId: 'v1.signer-prod.testnet',
  methodName: 'sign',
  args: {
    payload: Array.from(transactionHash),
    path: `bastion-users,${userId}`,    // Derivation path
    key_version: 0                       // Key version (0 = current)
  },

// MPC network produces threshold signature
// No single node knows the private key
```

2. **DAO state:** Export from NEAR contracts, import to Calimero contexts
