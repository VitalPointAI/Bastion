## Summary

This phase is a pure architectural reorganization of the frontend navigation. No new features are added, no backend changes are required, and no new libraries need to be installed. The existing stack — React 19, TypeScript, react-router-dom v7, and the existing CSS variable theming system — contains everything needed to execute this restructure cleanly.

The current navigation in `App.tsx` is implemented as a flat `useState`-based view switcher with parallel `Routes` entries for each view (no nested routing). The restructure introduces a two-level navigation hierarchy: five top tabs (Decide, Design, Campaign, Monitor, Admin) and a collapsible left sidebar within each tab for sub-component selection. This is a well-understood UI pattern with no external dependency requirements.

The primary implementation risk is component coupling and prop threading. Several components (`PlanningDashboard`, `MDMPGovernancePanel`) require mission-specific IDs to render, meaning they currently live inside `MissionDetail`. Moving them to a top-level Design or Campaign tab requires deciding whether those contexts are always mission-scoped (picker in sidebar) or global. Research reveals that `MissionDetail` is the primary container for `PlanningDashboard` — the new Campaign tab will need a mission-context mechanism to make these work at the top-level tab. The user's tab-to-component mapping document delineates where each component belongs, so the question is not "where" but "how to thread context."

**Primary recommendation:** Implement the sidebar as a local `useState` toggle within each tab container component (no global state needed). Use `useNavigate` + `useLocation` for URL sync of the active tab only; handle sidebar item selection as local component state (no sub-URLs for v1 — bookmarkability is low priority at this stage). Redirect old routes at the `App.tsx` Router level using `<Navigate>` components.

### Pattern 1: Shared TabLayout Component (Sidebar Shell)

**What:** A reusable layout wrapper that renders the left sidebar + content area. Each tab passes its own sidebar items and selected-component renderer.

**When to use:** All four main activity tabs. Admin is excluded — `AdminDashboard` already has its own internal tab UI.

**Example:**

```typescript
// frontend/src/components/tabs/TabLayout.tsx

interface SidebarItem {
  id: string;
  label: string;           // Doctrinal label shown in sidebar
  tooltip?: string;        // Shown for non-obvious doctrinal terms
}

interface TabLayoutProps {
  items: SidebarItem[];
  selectedItem: string;
  onSelectItem: (id: string) => void;
  children: React.ReactNode;  // The active component content
}

export function TabLayout({ items, selectedItem, onSelectItem, children }: TabLayoutProps) {
  const [sidebarOpen, setSidebarOpen] = useState(true);

  return (
    <div className="tab-layout">
      <aside className={`tab-sidebar ${sidebarOpen ? 'open' : 'collapsed'}`}>
        <button
          className="sidebar-toggle"
          onClick={() => setSidebarOpen(!sidebarOpen)}
          aria-label={sidebarOpen ? 'Collapse sidebar' : 'Expand sidebar'}
        >
          {sidebarOpen ? '‹' : '›'}
        </button>
        {sidebarOpen && (
          <nav className="sidebar-nav">
            {items.map(item => (
              <button
                key={item.id}
                className={`sidebar-item ${selectedItem === item.id ? 'active' : ''}`}
                onClick={() => onSelectItem(item.id)}
                title={item.tooltip}
              >
                {item.label}
              </button>
            ))}
          </nav>
        )}
      </aside>
      <main className="tab-content">
        {children}
      </main>
    </div>
  );
}
```

### Pattern 3: Top Navigation Tab Switching via React Router

**What:** The top-level tab bar uses `useNavigate` to push the tab path. The active tab is derived from `useLocation().pathname`, not from `useState`. This ensures URL always reflects the active tab and browser back/forward works.

**Example (App.tsx nav section):**

```typescript
// In AppContent — derive active tab from URL
import { useNavigate, useLocation } from 'react-router-dom';

const TABS = ['decide', 'design', 'campaign', 'monitor'] as const;
type MainTab = typeof TABS[number];

function AppContent() {
  const navigate = useNavigate();
  const location = useLocation();

  // Derive active tab from pathname
  const activeTab = TABS.find(tab => location.pathname.startsWith(`/${tab}`)) ?? 'monitor';

  return (
    <div className="app">
      <header className="app-header">
        <h1>BASTION</h1>
        <nav className="app-nav">
          {TABS.map(tab => (
            <button
              key={tab}
              className={`nav-button ${activeTab === tab ? 'active' : ''}`}
              onClick={() => navigate(`/${tab}`)}
            >
              {tab.charAt(0).toUpperCase() + tab.slice(1)}
            </button>
          ))}
          <button
            className={`nav-button nav-button--admin ${activeTab === 'admin' ? 'active' : ''}`}
            onClick={() => navigate('/admin')}
          >
            Admin
          </button>
        </nav>
        <UserStatusBar />
      </header>
      <main className="app-main">
        {activeTab === 'decide' && <DecideTab />}
        {activeTab === 'design' && <DesignTab />}
        {activeTab === 'campaign' && <CampaignTab />}
        {activeTab === 'monitor' && <MonitorTab />}
        {/* admin is handled by Route directly since it has its own AdminDashboard */}
      </main>
    </div>
  );
}
```

### Pattern 5: Mission Context for Campaign Tab

**What:** `PlanningDashboard` and `MDMPGovernancePanel` require a `missionId`. In the current design they live inside `MissionDetail`. In the Campaign tab, the sidebar will list missions (same as the current `MissionList`) and selecting one switches to the detail view.

**How to handle:** Keep the mission selection flow inside `CampaignTab` as local state — `selectedMissionId`. When no mission is selected, show `MissionList`. When a mission is selected, show `MissionDetail` (which internally renders `PlanningDashboard`). This preserves the existing prop patterns exactly and avoids any refactoring of MissionDetail.

### Anti-Patterns to Avoid

- **Removing `<Routes>` and switching to pure `useState` navigation globally:** The app already uses react-router for auth redirects (`useLocation` in `AuthWrapper`, `<Navigate to="/login">`) — these depend on the router context. Do not remove Routes.
- **Using `react-tabs` for the top navigation:** `react-tabs` is used inside `AdminDashboard` and `MissionDetail` for sub-component tabs. Using it for the top-level nav would add unnecessary complexity and fight the URL-sync pattern. Keep the top nav as `<button>` elements with `useNavigate`.
- **Adding URL sub-routes for sidebar items in v1:** Sub-routes like `/monitor/actor-graph` require additional Route definitions and add complexity without meaningful bookmark benefit at this stage. Use local `useState` for sidebar item selection in v1. Can be added later without architectural changes.
- **Moving existing component files:** Do not move `DAODashboard.tsx`, `StrategicDashboard.tsx`, etc. The new tab containers (`DecideTab`, `DesignTab`, etc.) import them. Zero churn on existing component files.
- **Removing the `onBack` prop from AdminDashboard:** `AdminDashboard` currently receives `onBack`. With top-level routing, `onBack` can navigate to `/monitor` via `useNavigate`. Keep the prop, wire it to navigate.

## Common Pitfalls

### Pitfall 1: Auth Route Breakage
**What goes wrong:** After restructuring, the AuthWrapper redirect logic (`<Navigate to="/login" state={{ from: location }} replace />`) must still work. If the Route structure changes incorrectly, `location.state.from` may point to an old route that no longer exists.
**Why it happens:** `AuthWrapper` reads `location` from the router to restore post-login destination.
**How to avoid:** After implementing redirects from old routes to new ones, test: visit `/governance` while logged out → should redirect to `/login` → after login should land at `/decide` (the redirect target). The `state={{ from: location }}` will capture `/governance` → but that will redirect to `/decide` anyway. Acceptable.
**Warning signs:** After login, page goes to an unexpected location or shows NotFound.

### Pitfall 2: `initialView` Prop Pattern Breaking
**What goes wrong:** `AppContent` currently uses `initialView` prop to set `useState` initial value. When switching to URL-driven navigation, the `initialView` prop approach is replaced. Any leftover `initialView` usage in Routes will be ignored.
**Why it happens:** The old pattern mixed `useState` with `Routes` in a non-standard way.
**How to avoid:** Remove `initialView` prop entirely. Active tab is always derived from `useLocation().pathname`.
**Warning signs:** TypeScript errors on removed prop, or navigation not working after login redirect.

### Pitfall 3: Sidebar State Reset on Tab Switch
**What goes wrong:** Every time the user clicks a different top tab, the tab container component unmounts and remounts, resetting the sidebar's open/closed state to default (open).
**Why it happens:** React unmounts the old tab component when switching tabs.
**How to avoid:** This is intentional per user decision ("sidebar open by default when entering a tab"). The sidebar resets to open on tab change, which is the correct behavior.
**Warning signs:** None — this is correct behavior, but could be confused for a bug.

### Pitfall 4: `MDMPGovernancePanel` Requiring Mission Context in Decide Tab
**What goes wrong:** `MDMPGovernancePanel` requires `missionId` and `daoId`. If placed in Decide tab without context, it errors.
**Why it happens:** Component designed to be used inside a mission context.
**How to avoid:** Add a mission/DAO selector at the top of the Decide tab (or Decide sidebar). When no mission is selected, show a picker prompt. When selected, render the panel. Same pattern used throughout MissionDetail.
**Warning signs:** Runtime errors about undefined missionId, empty governance panel.

### Pitfall 5: Admin Route Wildcard
**What goes wrong:** Admin route uses `/admin/*` wildcard. If this is changed to `/admin`, sub-paths within admin may break.
**Why it happens:** `AdminDashboard` uses react-tabs for internal navigation — those tabs don't use URLs, so the wildcard is more defensive than functional.
**How to avoid:** Keep `/admin/*` route unchanged. `AdminDashboard` is self-contained and doesn't need route changes.
**Warning signs:** Admin sub-navigation breaks, 404 on internal admin tab clicks.

### Pitfall 6: `ForceGraph2D` Height Calculation
**What goes wrong:** `GraphExplorer` uses `height={window.innerHeight - 60}` for the force graph canvas size. Inside the new sidebar layout, the available height is `window.innerHeight - headerHeight - sidebarHeaderHeight`.
**Why it happens:** Force-graph canvas needs explicit pixel height.
**How to avoid:** Pass height as a prop derived from the container's available height, or use a ResizeObserver to get actual container height. The current hardcoded `window.innerHeight - 60` will be wrong inside a layout with more chrome.
**Warning signs:** Graph canvas overflows content area, or is too short with empty space below.

## Open Questions

1. **MDMPGovernancePanel context in Decide tab**
   - What we know: Component requires `missionId` + `daoId`; currently embedded in DAODashboard via toggle button
   - What's unclear: Should the Decide tab surface MDMP governance for a selected mission (picker in sidebar), or should it remain accessible only through DAODashboard's toggle button?
   - Recommendation: Keep the current DAODashboard toggle button pattern for v1. This means the "MDMP Workflow" sidebar item in Decide just scrolls/focuses to the MDMPGovernancePanel that's already inside DAODashboard. Simplest path, least refactoring.

2. **PlanningDashboard context in Design tab**
   - What we know: `PlanningDashboard` requires `missionId`; currently rendered inside `MissionDetail`
   - What's unclear: The user's component mapping places StrategicDashboard (document ingestion) + PlanningDashboard (COA development) both under Design. These are very different contexts.
   - Recommendation: For v1, treat StrategicDashboard as the primary Design landing. PlanningDashboard stays embedded in MissionDetail (within Campaign). The Design tab sidebar item "COA Development" can link to Campaign with a note that COA work is done in the context of a selected mission. This avoids duplicating mission-context logic.

3. **GraphExplorer height inside sidebar layout**
   - What we know: Uses `height={window.innerHeight - 60}` hardcoded
   - What's unclear: How much header + sidebar chrome takes up
   - Recommendation: Use a `useRef` + `ResizeObserver` on the `.tab-content` div to get actual available height and pass it to GraphExplorer. This is a simple addition, not a research gap.

## State of the Art

| Old Approach | Current Approach | Impact |
|--------------|-----------------|--------|
| Tab navigation via `useState` | Tab navigation via `useNavigate` + `useLocation` | URL reflects active tab; browser back/forward works; deep linking works |
| Flat view switching (all views in one component) | Tab container components with sidebar | Each tab is a separate component; cleaner separation of concerns |
