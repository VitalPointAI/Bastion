## Architecture Decisions

### 1. RFC 6238 TOTP Implementation

**Decision:** Implement TOTP from scratch using Node.js crypto instead of using otplib dependency.

**Alternatives considered:**
- Use otplib library → Rejected: Already installed but reimplemented for learning/control
- Use speakeasy library → Rejected: Additional dependency

**Rationale:**
- Full control over algorithm implementation (HMAC-SHA1, dynamic truncation)
- Educational value - understanding RFC 6238 deeply
- No external dependency for critical security component
- Constant-time comparison built in
- Base32 encoding/decoding included

**Impact:** Complete TOTP implementation compatible with all major authenticator apps.

### 2. Magic Link as Multi-Purpose Mechanism

**Decision:** Magic links serve both PRF fallback and recovery email verification.

**Alternatives considered:**
- Separate token systems for fallback vs recovery → Rejected: Unnecessary complexity
- OTP codes instead of links → Rejected: Worse UX (manual typing)
- SMS-based verification → Rejected: Phone number requirement, SIM swap attacks

**Rationale:**
- Single token generation/verification flow
- `isRecovery` flag differentiates purpose
- 15-minute expiration + one-time use prevents abuse
- Email already required for registration
- Works in all environments (no phone needed)

**Impact:** Unified email verification for both fallback and recovery scenarios.

### 3. Multi-Factor Recovery Required

**Decision:** Recovery always requires Email + TOTP (if user has TOTP enabled).

**Alternatives considered:**
- Email-only recovery → Rejected: Single point of failure (email compromise)
- Allow skip if TOTP setup incomplete → Accepted: Necessary for users without 2FA

**Rationale:**
- Email compromise common (phishing, password reuse, breaches)
- TOTP provides independent second factor (physical device possession)
- Attackers with email access can't recover account without TOTP
- Bypass available for legacy users (with security warning)

**Impact:** Significantly stronger recovery security compared to email-only.

### 4. Deployment-Configurable 2FA Types

**Decision:** PlatformSettingsStore controls allowed second factors per environment.

**Alternatives considered:**
- Hardcoded TOTP-only → Rejected: Can't adapt to classified environments
- Per-user 2FA choice → Rejected: Inconsistent security posture

**Rationale:**
- Public: TOTP only (internet-facing, standard auth apps)
- Enterprise: TOTP or hardware token (Yubikey for corporate)
- Classified: Hardware token or CAC/PIV (SCIF environments, no phones)
- Admin-configurable via Admin UI
- Phase 1.2 implements TOTP; hardware tokens deferred to future phase

**Impact:** Single codebase supports multiple deployment security levels.

### 5. Recovery Token Pattern

**Decision:** Separate recovery token after TOTP verification authorizes passkey replacement.

**Alternatives considered:**
- Direct passkey deletion after TOTP → Rejected: Race condition if registration fails
- Session-based authorization → Rejected: Session expiration complexity

**Rationale:**
- Email verified → limited session
- TOTP verified → recovery token (15 min TTL)
- Recovery token authorizes passkey deletion + new registration
- Token consumed immediately after use
- Prevents partial recovery state corruption

**Impact:** Atomic recovery flow with clear authorization boundaries.

### 6. NEAR Account Preservation During Recovery

**Decision:** Passkey deletion doesn't affect NEAR account (MPC uses UUID, not passkey).

**Alternatives considered:**
- Derive NEAR account from passkey → Rejected: Recovery would orphan assets
- Require backup codes for recovery → Rejected: Users lose codes frequently

**Rationale:**
- User UUID is stable identifier for MPC derivation path (`bastion,{uuid}`)
- UUID never changes even when passkey changes
- MPC derives same NEAR signing key from same UUID
- Recovery process: delete old passkey → register new passkey → same UUID → same NEAR account
- Assets preserved across recovery

**Impact:** True account recovery without asset loss.

## Technical Highlights

### TOTP Implementation (RFC 6238)

```typescript
// Generate 6-digit TOTP code with clock drift tolerance
private generateCode(secret: string, timeStep: number): string {
  const secretBytes = this.base32Decode(secret);
  const timeBuffer = Buffer.alloc(8);
  timeBuffer.writeBigUInt64BE(BigInt(timeStep));

  // HMAC-SHA1 (standard for authenticator apps)
  const hmac = createHmac('sha1', secretBytes);
  hmac.update(timeBuffer);
  const hash = hmac.digest();

  // Dynamic truncation (RFC 4226)
  const offset = hash[hash.length - 1] & 0x0f;
  const code = (
    ((hash[offset] & 0x7f) << 24) |
    ((hash[offset + 1] & 0xff) << 16) |
    ((hash[offset + 2] & 0xff) << 8) |
    (hash[offset + 3] & 0xff)
  ) % Math.pow(10, 6);

  return code.toString().padStart(6, '0');
}
```

### Magic Link Recovery Flow

```typescript
// Step 1: Initiate recovery (email verification)
POST /api/auth/recovery/initiate
{ email: "user@example.com" }
→ Magic link sent to email
→ Returns { requiresTotp: true } if user has 2FA enabled

// Step 2: Click magic link → limited session created
POST /api/auth/magic-link/verify
{ token: "..." }
→ Returns { sessionToken: "...", requiresTotpVerification: true }

// Step 3: Verify TOTP code
POST /api/auth/recovery/verify-totp
Headers: Authorization: Bearer <sessionToken>
{ code: "123456" }
→ Returns { verified: true, recoveryToken: "rec_..." }

// Step 4: Authorize passkey replacement
POST /api/auth/recovery/authorize-passkey
{ recoveryToken: "rec_..." }
→ Old passkeys deleted, ready for new passkey registration
```

### Constant-Time Comparison (Timing Attack Prevention)

```typescript
private constantTimeCompare(a: string, b: string): boolean {
  if (a.length !== b.length) return false;

  let result = 0;
  for (let i = 0; i < a.length; i++) {
    result |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return result === 0;
}
```
