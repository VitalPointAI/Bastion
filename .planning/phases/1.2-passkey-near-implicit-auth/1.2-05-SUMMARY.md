## Architecture Notes

### Auth Flow Comparison

**Old (Privy):**
1. User logs in via Privy (OAuth, email, wallet)
2. Frontend calls /api/accounts/create with Privy user ID
3. Backend creates NEAR account from Privy UUID
4. Frontend registers with MPC for key backup
5. Frontend creates DID

**New (Passkey):**
1. User authenticates with passkey or magic link
2. Backend creates NEAR account from user UUID (not passkey)
3. Backend handles MPC registration automatically
4. Frontend extracts PRF output for DID operations
5. Frontend creates DID if PRF available

### PRF-Based DID Operations

The PRF (Pseudo-Random Function) extension provides:
- Deterministic secret derived from passkey
- Used for DID document signing and encryption
- Falls back to magic link when PRF unavailable (limited functionality)

### Session Management

- Session token stored in localStorage
- AuthService singleton manages token lifecycle
- useAuth hook restores session on mount
- Automatic session refresh on page reload

### Component Hierarchy

```
AuthWrapper (provides AuthProvider)
└── AuthContent (auth logic + UserProvider)
    └── App components (use useAuth hook)
```
