# Phase 1.2 Plan 06: Migration Flow Summary

**One-liner:** DID migration service for re-encrypting DIDs when userSecret derivation changes, with REST API and UI component

## What Was Built

### MigrationService (backend/src/auth/migration-service.ts)
**Purpose:** Handle DID re-encryption when userSecret derivation method changes

**Key capabilities:**
- `getMigrationStatus()` - Check if user needs migration
- `migrateDID()` - Decrypt DID with old secret, re-encrypt with new
- `deriveLegacyUserSecret()` - Example pattern for old secret derivation
- Handles both same-account and different-account migrations
- Preserves DID document content during migration

**Architecture:**
- Singleton pattern with lazy initialization
- Uses existing DIDService for encryption/decryption
- Works with UserStore and PasskeyStore
- Generic pattern - not tied to specific auth provider

### Migration API Endpoints (backend/src/api/auth.ts)
**Added endpoints:**
- `GET /api/auth/migration/status` - Check migration status for user
- `POST /api/auth/migration/migrate` - Perform DID re-encryption

**Security:**
- Validates secret format (base64)
- Enforces 32-byte secret length
- Returns success/failure with DID preservation status

### MigrationFlow Component (frontend)
**Purpose:** Guide users through security upgrade migrations

**Features:**
- Multi-step flow: intro → processing → TOTP setup → complete
- Error handling with retry capability
- Skip option for deferring migrations
- Generic component - reusable for various migration types
- Military-themed CSS matching existing UI

**States:**
- `intro` - Explain upgrade benefits
- `processing` - Show migration progress
- `totp-setup` - Prompt for 2FA setup (optional)
- `complete` - Success message
- `error` - Error with retry option

## Technical Implementation

### DID Migration Flow
```
1. User authenticates with old method → derives oldSecret
2. User authenticates with new method → derives newSecret
3. API receives both secrets (base64-encoded)
4. Backend decrypts DID with oldSecret
5. Backend re-encrypts DID with newSecret
6. Same blinded key on-chain → DID updated
7. User marked as migrated
```

### Key Design Decisions

**Why generic migration service?**
- Original plan assumed Privy migration
- System doesn't use Privy (already removed in earlier plans)
- Created generic pattern for future migration scenarios:
  - Upgrading secret derivation methods
  - Security-mandated secret rotation
  - Legacy system migrations

**Why base64 encoding for secrets?**
- Standard for binary data in JSON APIs
- Client-side PRF output is already base64url
- Easy to validate and decode server-side

**Why strict 32-byte validation?**
- Matches HKDF output length (Phase 2 DID system)
- Matches encryption key requirements
- Prevents subtle bugs from incorrect secret lengths

## Use Cases

### Scenario 1: Upgrading to PRF-based DID encryption
User has DID encrypted with legacy secret derivation, needs to migrate to PRF-based:
1. User logs in with old method
2. System derives oldSecret from legacy auth
3. User sets up passkey with PRF
4. System extracts PRF output as newSecret
5. Call `/api/auth/migration/migrate` with both secrets
6. DID re-encrypted, user can now use PRF-based auth

### Scenario 2: Security-mandated secret rotation
Organization requires periodic secret rotation:
1. Generate new secret via updated derivation method
2. Call migration endpoint with old and new secrets
3. All DIDs re-encrypted with new secret
4. Old secrets can be decommissioned

### Scenario 3: Passkey replacement during recovery
User lost passkey device, sets up new passkey:
- NEAR account preserved (MPC uses UUID, not passkey)
- DID needs re-encryption if PRF output changed
- Migration service handles DID update
