## Architecture Decisions

### 1. Passkeys for Authentication ONLY (Not NEAR Derivation)

**Decision:** Passkeys verify user identity; they do NOT derive NEAR account IDs.

**Alternatives considered:**
- Derive NEAR implicit account from passkey public key → Rejected: breaks recovery (new passkey = new account = orphaned assets)
- Store passkey private key for NEAR signing → Rejected: WebAuthn doesn't expose private keys

**Rationale:**
- Passkey loss/replacement common (device upgrade, loss, damage)
- New passkey = new public key
- If NEAR account tied to passkey public key, recovery impossible
- MPC with stable UUID solves this: same UUID → same MPC path → same signing key

**Impact:** Clean separation of concerns: passkeys for auth, MPC for NEAR signing.

### 2. MPC-Based NEAR Account Creation with UUID Derivation

**Decision:** NEAR accounts created via Chain Signatures MPC using stable UUID-based derivation path.

**Alternatives considered:**
- Passkey-derived NEAR accounts → Rejected: breaks recovery (see Decision 1)
- Email-based derivation → Rejected: email can change
- Privy user ID derivation → Rejected: removing vendor dependency

**Rationale:**
- UUID is stable identifier (never changes)
- MPC derivation path format: `bastion,{uuid}`
- Same UUID = same path = same NEAR account = assets preserved
- User can recover account access by re-registering passkey (same UUID = same MPC path)

**Impact:** True account recovery without orphaning NEAR accounts.

### 3. PRF Extension for DID Secret Derivation

**Decision:** Request PRF extension during registration and authentication for DID operations.

**Alternatives considered:**
- No PRF support → Rejected: limits DID functionality
- Require PRF → Rejected: browser compatibility issues
- Separate DID credential → Rejected: added complexity

**Rationale:**
- PRF extension provides deterministic secret derivation from passkey
- Used for DID operations (separate from NEAR account)
- Detected and stored during registration (prfSupported flag)
- Evaluated during authentication with RP ID as salt
- PRF not required for basic authentication (graceful degradation)

**Impact:** DID functionality available on PRF-capable devices, graceful fallback for others.

### 4. In-Memory Challenge Store (v1)

**Decision:** Store WebAuthn challenges in-memory Map with 5-minute TTL.

**Alternatives considered:**
- Redis for challenge storage → Deferred: overkill for v1, consider for production
- Database storage → Rejected: too slow for 5-minute TTL
- No expiration → Rejected: security risk

**Rationale:**
- Challenges are short-lived (5 minutes)
- In-memory sufficient for v1 development
- Simple cleanup mechanism (cleanupExpiredChallenges)
- Production: migrate to Redis for multi-instance deployments

**Impact:** Simple v1 implementation, migration path clear for production.

## Technical Highlights

### MPC Derivation Path Generation

```typescript
// User UUID is stable anchor (never changes)
export function getMPCDerivationPath(userId: string): string {
  return `bastion,${userId}`;
}

// Account ID format: bastion-{first-8-uuid}.testnet
const accountIdPrefix = `bastion-${userId.slice(0, 8).toLowerCase()}`;
const accountId = NEAR_NETWORK_ID === 'mainnet'
  ? `${accountIdPrefix}.near`
  : `${accountIdPrefix}.testnet`;
```

### Passkey Registration Flow

```typescript
// 1. Generate registration options
const options = await generateRegistrationOptions({
  rpName: 'BASTION',
  rpID: 'localhost',
  userID: new TextEncoder().encode(user.id),
  userName: email,
  excludeCredentials,  // Prevent duplicate credentials
  extensions: { prf: {} }  // Request PRF for DID
});

// 2. Verify registration and store credential
const verification = await verifyRegistrationResponse({
  response,
  expectedChallenge,
  expectedOrigin,
  expectedRPID
});

// 3. Create NEAR account via MPC (separate from passkey)
const { accountId, derivationPath } = await createMPCAccount(userId);
```

### Passkey Authentication Flow

```typescript
// 1. Generate authentication options
const options = await generateAuthenticationOptions({
  rpID: 'localhost',
  allowCredentials,  // User's registered credentials
  extensions: {
    prf: {
      eval: {
        // Deterministic salt for DID secret derivation
        first: new TextEncoder().encode(`bastion-did-v1:${RP_ID}`)
      }
    }
  }
});

// 2. Verify authentication
const verification = await verifyAuthenticationResponse({
  response,
  expectedChallenge,
  expectedOrigin,
  expectedRPID,
  credential  // From database
});

// 3. Update counter (replay prevention)
await passkeyStore.updateCounter(credential.id, newCounter);

// 4. Extract PRF output if available
const prfResult = response.clientExtensionResults?.prf?.results?.first;
if (prfResult) {
  prfOutput = new Uint8Array(isoBase64URL.toBuffer(prfResult));
}

// 5. Create session
const session = await sessionStore.createSession({
  userId,
  nearAccountId,
  prfAvailable: prfOutput !== null
});
```

### Account Recovery Preserves Assets

```typescript
// OLD PASSKEY LOST:
// User loses device with passkey
// Credential ID changes, public key changes

// RECOVERY FLOW:
// 1. Recovery via email + TOTP (plan 1.2-03)
// 2. Delete old passkeys: await passkeyStore.deleteAllForUser(userId)
// 3. Register NEW passkey: new credentialId, new publicKey
// 4. BUT: Same userId = same MPC path = same NEAR account
const mpcPath = getMPCDerivationPath(userId);  // bastion,{same-uuid}
// Result: User can access their NEAR account with new passkey
```

## REST API Endpoints

### Passkey Registration

**POST /api/auth/passkey/register-options**
- Body: `{ email: string, isRecovery?: boolean }`
- Response: `{ options, challengeId, userId }`
- Purpose: Generate WebAuthn registration challenge

**POST /api/auth/passkey/register**
- Body: `{ challengeId, userId, response: RegistrationResponseJSON }`
- Response: `{ verified, nearAccountId, prfSupported, mpcDerivationPath }`
- Purpose: Verify registration and create MPC NEAR account

### Passkey Authentication

**POST /api/auth/passkey/auth-options**
- Body: `{ email?: string }`
- Response: `{ options, challengeId }`
- Purpose: Generate WebAuthn authentication challenge

**POST /api/auth/passkey/authenticate**
- Body: `{ challengeId, response: AuthenticationResponseJSON }`
- Response: `{ verified, sessionToken, nearAccountId, prfAvailable }`
- Purpose: Verify authentication and create session

### Session Management

**GET /api/auth/session**
- Headers: `Authorization: Bearer <sessionToken>`
- Response: `{ userId, nearAccountId, prfAvailable, expiresAt }`
- Purpose: Get current session info

**POST /api/auth/logout**
- Headers: `Authorization: Bearer <sessionToken>`
- Response: `{ success: true }`
- Purpose: Delete session (logout)
