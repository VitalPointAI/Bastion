# Phase 1.2: Passkey Authentication & NEAR Implicit Accounts - Research

**Researched:** 2026-02-01
**Domain:** WebAuthn passkey authentication, NEAR implicit accounts, DID integration
**Confidence:** HIGH

## Summary

This research addresses the critical challenge of replacing Privy.io authentication with a self-sovereign passkey-based system while maintaining compatibility with the existing DID framework. The core technical problem is that **passkeys (WebAuthn credentials) do not expose private key material**, yet the current DID system requires a NEAR private key to derive the `userSecret` via HKDF.

The solution involves three integrated technologies:
1. **NEAR Implicit Accounts** - Account IDs derived directly from ED25519 public keys (64-char hex)
2. **WebAuthn Passkeys** - Hardware-backed authentication with @simplewebauthn library
3. **PRF Extension** - Deterministic secret derivation from passkey credentials for DID operations

**CRITICAL FINDING:** The WebAuthn PRF (Pseudo-Random Function) extension enables deterministic secret generation from passkey credentials without exposing private keys. This solves the DID integration challenge by providing a stable `userSecret` derivation mechanism compatible with the existing HKDF-based DID system.

**Primary recommendation:** Use WebAuthn passkeys with PRF extension for authentication and DID secret derivation. Derive NEAR implicit account IDs from passkey public keys. Implement magic links as fallback authentication for recovery scenarios. Migration path preserves existing Privy user DIDs through temporary dual-authentication support.

### Pattern 1: NEAR Implicit Account Derivation from Passkey Public Key

**What:** Convert WebAuthn ED25519 public key to NEAR implicit account ID (64-char hex)

**When to use:** During passkey registration, when user creates first credential

**How it works:**
1. User registers passkey → WebAuthn returns credential with public key
2. Extract ED25519 public key from COSE structure (SimpleWebAuthn provides parsed key)
3. Convert 32-byte public key to hex string (64 characters)
4. Result is NEAR implicit account ID: `account_id = publicKey.hex()`

**Example:**
```typescript
// Source: NEAR Implicit Accounts Documentation
// https://docs.near.org/integrations/implicit-accounts

import { isoBase64URL } from '@simplewebauthn/server/helpers';

async function deriveImplicitAccountId(
  credentialPublicKey: Uint8Array
): Promise<string> {
  // SimpleWebAuthn returns ED25519 public key as 32 bytes
  // For NEAR implicit accounts: accountId = hex(publicKey)

  // Convert bytes to hex (lowercase)
  const hexAccountId = Buffer.from(credentialPublicKey)
    .toString('hex')
    .toLowerCase();

  // NEAR implicit account ID format:
  // - ED25519: 64 hex characters (32 bytes)
  // - Secp256k1: 0x + keccak256(pubkey)[12:32].hex()

  console.log('NEAR Implicit Account ID:', hexAccountId);
  return hexAccountId; // Returns 64-char hex string
}

// After passkey registration:
const { credential } = verification.registrationInfo;
const implicitAccountId = await deriveImplicitAccountId(credential.publicKey);

// Account automatically exists on NEAR (no registration needed)
// First transaction to this account creates it on-chain
```

**Source:** [NEAR Implicit Accounts Documentation](https://docs.near.org/integrations/implicit-accounts)

### Pattern 2: PRF Extension for Deterministic Secret Derivation

**What:** Use WebAuthn PRF extension to derive deterministic secrets from passkey credentials for DID operations

**When to use:** After successful passkey authentication, when deriving `userSecret` for DID encryption/blinded key operations

**Critical insight:** PRF solves the "no private key access" problem by providing deterministic HMAC-based secret generation.

**How it works:**
1. During authentication, request PRF extension with salt input
2. Authenticator computes HMAC with hardware-backed secret key
3. Returns 32-byte deterministic output (same inputs = same output)
4. Use output as `userSecret` for HKDF derivation in DID system

**Example:**
```typescript
// Source: Corbado WebAuthn PRF Guide
// https://www.corbado.com/blog/passkeys-prf-webauthn

import { generateAuthenticationOptions, verifyAuthenticationResponse } from '@simplewebauthn/server';

// Step 1: Generate authentication options with PRF extension
async function generateAuthWithPRF(accountId: string) {
  const options = await generateAuthenticationOptions({
    rpID: 'example.com',
    // Request PRF extension
    extensions: {
      prf: {
        eval: {
          // Salt for DID derivation (use accountId for consistency)
          first: new TextEncoder().encode(`bastion-did-v1:${accountId}`)
        }
      }
    }
  });

  return options;
}

// Step 2: Client-side authentication (browser)
// frontend/src/lib/passkey.ts
import { startAuthentication } from '@simplewebauthn/browser';

async function authenticateWithPRF(options) {
  const credential = await startAuthentication({ optionsJSON: options });

  // Check if PRF was successful
  const prfResults = credential.clientExtensionResults?.prf;
  if (prfResults?.results?.first) {
    console.log('PRF secret derived:', prfResults.results.first);
    // This is the deterministic 32-byte secret
    // Send to backend for DID operations
  }

  return credential;
}

// Step 3: Backend verification and DID operations
async function verifyAndDeriveDIDSecret(
  response: AuthenticationResponseJSON,
  accountId: string
) {
  // Verify passkey authentication
  const verification = await verifyAuthenticationResponse({
    response,
    expectedChallenge,
    expectedOrigin,
    expectedRPID
  });

  if (!verification.verified) {
    throw new Error('Authentication failed');
  }

  // Extract PRF result from client extension results
  // NOTE: PRF output is computed client-side, sent in response
  const prfOutput = response.clientExtensionResults?.prf?.results?.first;

  if (!prfOutput) {
    throw new Error('PRF extension not available - fallback to magic link');
  }

  // Convert base64url to Uint8Array
  const userSecret = isoBase64URL.toBuffer(prfOutput);

  // Now use userSecret with existing DID system
  const { deriveDIDBlindedKey, deriveEncryptionKey } = await import('./identity/blinded-keys.js');

  const blindedKey = deriveDIDBlindedKey(userSecret, accountId);
  const encryptionKey = deriveEncryptionKey(userSecret);

  return { userSecret, blindedKey, encryptionKey };
}
```

### Pattern 3: Magic Link Authentication (Fallback & Recovery)

**What:** Email-based one-time link authentication for PRF-unsupported devices and account recovery

**When to use:**
- Browser/authenticator doesn't support PRF extension
- User lost passkey device (recovery flow)
- Initial email verification before passkey setup

**Example:**
```typescript
// Source: StratBrain magicLink.ts (reference implementation)
// /home/vitalpointai/projects/Comps/server/src/services/magicLink.ts

import crypto from 'crypto';

const MAGIC_LINK_EXPIRY_MINUTES = 15;

interface MagicLinkToken {
  token: string;
  email: string;
  expiresAt: Date;
  used: boolean;
}

// Create magic link token
export async function createMagicLink(email: string): Promise<string> {
  // Generate secure random token (32 bytes = 64 hex chars)
  const token = crypto.randomBytes(32).toString('hex');

  // Calculate expiry
  const expiresAt = new Date(Date.now() + MAGIC_LINK_EXPIRY_MINUTES * 60 * 1000);

  // Invalidate existing unused tokens for this email
  await db.magicLinkToken.updateMany({
    where: { email, used: false },
    data: { used: true }
  });

  // Store token
  await db.magicLinkToken.create({
    data: { token, email, expiresAt }
  });

  return token; // Caller builds URL: https://app.com/auth/verify?token=...
}

// Verify magic link token
export async function verifyMagicLink(token: string): Promise<string | null> {
  const record = await db.magicLinkToken.findUnique({
    where: { token }
  });

  if (!record) return null;
  if (record.used) return null;
  if (record.expiresAt < new Date()) return null;

  // Mark as used (one-time use)
  await db.magicLinkToken.update({
    where: { token },
    data: { used: true }
  });

  return record.email; // Return email for account lookup
}
```

**Source:** [Email Magic Links - Clerk](https://clerk.com/blog/magic-links)

### Pattern 4: Passkey Account Recovery Flow

**What:** Email verification + passkey re-registration after device loss

**When to use:** User lost passkey device, needs to regain account access

**Flow:**
1. User requests recovery via email
2. Send magic link to verified email
3. User clicks link → authenticated via email
4. Prompt to register NEW passkey on current device
5. Delete old passkey credentials from database
6. **CRITICAL:** DID continuity preserved because implicit account ID remains the same

**Example:**
```typescript
// Source: StratBrain passkey.ts recovery pattern
// /home/vitalpointai/projects/Comps/server/src/services/passkey.ts

export async function generatePasskeyRegistrationOptions(
  userId: string,
  isRecovery: boolean = false
) {
  const user = await db.user.findUnique({
    where: { id: userId },
    include: { passkeys: true }
  });

  if (!user) throw new Error('User not found');
  if (!user.emailVerified) throw new Error('Email not verified');

  // For recovery: delete existing passkeys so user can register fresh
  if (isRecovery && user.passkeys.length > 0) {
    await db.passkeyCredential.deleteMany({
      where: { userId }
    });
    // Return empty excludeCredentials since we just deleted them
  }

  const options = await generateRegistrationOptions({
    rpName: 'BASTION',
    rpID: 'bastion.near',
    userID: new TextEncoder().encode(user.id),
    userName: user.email,
    userDisplayName: user.email.split('@')[0],
    excludeCredentials: isRecovery ? [] : user.passkeys.map(cred => ({
      id: isoBase64URL.fromBuffer(Buffer.from(cred.credentialId))
    }))
  });

  return options;
}
```

### Pattern 5: DID Integration with PRF-Derived Secrets

**What:** Integrate PRF-derived secrets with existing HKDF-based DID system

**When to use:** After successful passkey authentication with PRF support

**Critical insight:** PRF output serves as the `userSecret` input to existing DID derivation functions. No changes needed to DID encryption/blinding logic.

**Example:**
```typescript
// NEW: backend/src/identity/passkey-did.ts
import { deriveDIDBlindedKey, deriveEncryptionKey } from './blinded-keys.js';
import { DIDService } from './did-service.js';

/**
 * Create DID using PRF-derived secret
 * Maintains compatibility with existing DID system
 */
export async function createDIDFromPasskey(
  accountId: string,
  prfSecret: Uint8Array, // 32-byte output from PRF extension
  publicKeyBase58: string
): Promise<{ did: string; blindedKey: string }> {
  // prfSecret replaces the old NEAR-private-key-derived userSecret
  // Everything else remains unchanged

  const didService = new DIDService();

  const result = await didService.createDID(
    accountId,
    'Human', // entityType
    prfSecret, // userSecret (PRF-derived instead of NEAR-key-derived)
    publicKeyBase58
  );

  return result;
}

/**
 * Resolve DID using PRF-derived secret
 */
export async function resolveDIDFromPasskey(
  accountId: string,
  prfSecret: Uint8Array
) {
  const didService = new DIDService();
  return didService.resolveDID(accountId, prfSecret);
}

// MIGRATION: For Privy users without passkeys
export async function deriveUserSecretFromPrivyId(privyUserId: string): Promise<Uint8Array> {
  // Temporary migration path: derive userSecret from Privy user ID
  // This allows existing DIDs to remain accessible during transition

  const { hkdf } = await import('@noble/hashes/hkdf');
  const { sha256 } = await import('@noble/hashes/sha2');
  const { utf8ToBytes } = await import('@noble/hashes/utils');

  const salt = utf8ToBytes('bastion-privy-migration');
  const info = utf8ToBytes('privy-to-passkey-v1');
  const ikm = utf8ToBytes(privyUserId);

  return hkdf(sha256, ikm, salt, info, 32);
}
```

**Key architectural decision:** PRF extension output is cryptographically equivalent to the previous NEAR-private-key-derived secret. Both produce 32-byte deterministic values suitable for HKDF input. This maintains backward compatibility with the existing DID encryption and blinding system from Phase 2.

### Anti-Patterns to Avoid

- **Don't derive userSecret from credential ID:** Credential ID is random, not suitable for deterministic derivation
- **Don't store NEAR private keys:** Defeats purpose of passkeys; use PRF extension instead
- **Don't implement custom CBOR/COSE parsing:** Use SimpleWebAuthn's parsed structures
- **Don't skip PRF fallback handling:** Magic link must work when PRF unavailable
- **Don't modify existing DID encryption:** Only change userSecret derivation source

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| WebAuthn attestation verification | Custom COSE/CBOR decoder | @simplewebauthn/server | Handles all attestation formats (Packed, TPM, Android, Apple, FIDO U2F), COSE key parsing, challenge verification |
| Magic link token generation | Timestamp-based tokens | crypto.randomBytes(32) | Cryptographically secure random, prevents prediction attacks |
| NEAR implicit account creation | Manual transaction crafting | near-api-js utils | Handles account existence checks, proper key encoding, transaction formatting |
| PRF salt generation | Simple string concatenation | HKDF with proper context | Prevents cross-context attacks, domain separation |
| Session management | Cookie-based auth | HttpOnly secure cookies + Redis | Prevents XSS attacks, session fixation, CSRF |

**Key insight:** Passkey authentication involves complex cryptographic operations (CBOR encoding, COSE keys, attestation verification, challenge management). SimpleWebAuthn abstracts this complexity reliably. Custom implementations have high security risk.

## Common Pitfalls

### Pitfall 1: PRF Extension Not Available

**What goes wrong:** Authenticator or browser doesn't support PRF extension, userSecret derivation fails, DID operations blocked

**Why it happens:** PRF extension is relatively new (2023+), not all authenticators implement it. Platform authenticators (Windows Hello, iOS Face ID pre-18) may lack support.

**How to avoid:**
1. Check PRF support during registration: `credential.clientExtensionResults?.prf`
2. Store PRF capability flag per credential in database
3. Implement magic link fallback for PRF-unsupported credentials
4. Display clear messaging: "For full security features, use Chrome/Safari 18+"

**Warning signs:**
- User registers passkey but PRF results always undefined
- DID creation fails after successful authentication
- Users on older iOS/Windows devices reporting login issues

**Code example:**
```typescript
// After passkey registration
const verification = await verifyRegistrationResponse({...});

const prfSupported = response.clientExtensionResults?.prf?.enabled === true;

await db.passkeyCredential.create({
  data: {
    credentialId: Buffer.from(credential.id),
    publicKey: Buffer.from(credential.publicKey),
    counter: BigInt(credential.counter),
    prfSupported, // Store capability flag
    userId
  }
});

// During authentication
if (!credential.prfSupported) {
  // Use magic link flow instead
  return sendMagicLink(user.email);
}
```

### Pitfall 2: NEAR Implicit Account Key Mismatch

**What goes wrong:** Public key used for implicit account ID doesn't match passkey's actual public key, account creation fails or authentication breaks

**Why it happens:** WebAuthn can use different key algorithms (ES256, RS256, EdDSA). NEAR implicit accounts require ED25519 specifically. Algorithm mismatch causes wrong account ID derivation.

**How to avoid:**
1. Configure SimpleWebAuthn to REQUIRE EdDSA algorithm during registration
2. Reject non-ED25519 credentials with clear error message
3. Validate credential algorithm before deriving account ID

**Warning signs:**
- Account ID doesn't match expected 64-character hex format
- NEAR transactions fail with "account not found" despite registration
- Implicit account exists but can't sign transactions

**Code example:**
```typescript
// Configure WebAuthn to require EdDSA (ED25519)
const registrationOptions = await generateRegistrationOptions({
  rpName: 'BASTION',
  rpID: 'bastion.near',
  userID: userId,
  // CRITICAL: Require EdDSA for NEAR compatibility
  authenticatorSelection: {
    authenticatorAttachment: 'platform', // or 'cross-platform'
    residentKey: 'preferred',
    userVerification: 'preferred'
  },
  // Only allow EdDSA algorithm
  supportedAlgorithmIDs: [-8] // COSE algorithm ID for EdDSA
});

// Verify algorithm after registration
const { credential } = verification.registrationInfo;

// SimpleWebAuthn doesn't expose algorithm directly
// Check COSE key structure
if (credential.publicKey[1] !== 1) { // kty: OKP
  throw new Error('Only EdDSA (ED25519) keys supported for NEAR');
}
```

**IMPORTANT NOTE:** As of 2026, EdDSA support in WebAuthn is limited. YubiKey 5.2+ supports it, but many platform authenticators (iPhone, Windows Hello) only support ES256 (P-256). This creates a compatibility challenge.

**Recommended approach:**
1. Primary: Support ES256 (P-256) for compatibility
2. Convert P-256 public key to NEAR Secp256k1 implicit account format
3. Account ID = `'0x' + keccak256(publicKey)[12:32].hex()`
4. Fall back to named accounts if implicit conversion fails

### Pitfall 3: Credential ID Storage Format Mismatch

**What goes wrong:** Credential ID stored as base64url string but queried as binary, or vice versa. Lookups fail during authentication.

**Why it happens:** SimpleWebAuthn v13+ changed credential ID format from Buffer to base64url string. Database comparison must match format.

**How to avoid:**
1. Store credential ID as BYTES in database (not string)
2. Convert base64url to Buffer before storage
3. Use hex comparison for database lookups (SQLite/LibSQL compatibility)

**Warning signs:**
- Registration succeeds but authentication always fails with "credential not found"
- Database contains credentials but hex comparison doesn't match
- Different credential ID format between registration and authentication

**Code example:**
```typescript
// Source: StratBrain passkey.ts pattern
import { isoBase64URL } from '@simplewebauthn/server/helpers';

// During registration - STORE AS BYTES
const credIdBuffer = Buffer.from(isoBase64URL.toBuffer(credential.id));
await db.passkeyCredential.create({
  data: {
    credentialId: credIdBuffer, // Store as bytes
    publicKey: Buffer.from(credential.publicKey),
    counter: BigInt(credential.counter),
    userId
  }
});

// During authentication - COMPARE AS HEX
const credentialIdBuffer = Buffer.from(isoBase64URL.toBuffer(response.id));
const lookupHex = credentialIdBuffer.toString('hex');

// Fetch all credentials and compare manually (Prisma/SQLite limitation)
const credentials = await db.passkeyCredential.findMany({
  include: { user: true }
});

const credential = credentials.find(cred =>
  Buffer.from(cred.credentialId).toString('hex') === lookupHex
);
```

### Pitfall 4: DID Migration Breaks Existing Users

**What goes wrong:** Switching from Privy-derived userSecret to PRF-derived userSecret changes blinded keys, existing DIDs become inaccessible

**Why it happens:** DID blinded key is derived from `HKDF(userSecret, accountId, 'bastion-did-v1')`. Changing userSecret derivation source changes blinded key, can't decrypt existing DIDs.

**How to avoid:**
1. Implement dual-authentication period: support both Privy and passkey login
2. Migrate user DIDs explicitly: decrypt with old secret, re-encrypt with new
3. Store migration status flag per user
4. Provide clear migration flow in UI

**Warning signs:**
- Existing users report "DID not found" after passkey setup
- DID decryption fails with old encrypted documents
- User data inaccessible after migration

**Code example:**
```typescript
// backend/src/api/auth.ts - Migration endpoint
router.post('/migrate-to-passkey', async (req, res) => {
  const { privyUserId, prfSecret } = req.body;

  // Step 1: Get old userSecret (Privy-derived)
  const oldUserSecret = await deriveUserSecretFromPrivyId(privyUserId);

  // Step 2: Get user's NEAR account ID
  const user = await db.user.findUnique({ where: { privyUserId } });
  if (!user) throw new Error('User not found');

  // Step 3: Decrypt DID with old secret
  const didService = new DIDService();
  const oldDID = await didService.resolveDID(user.accountId, oldUserSecret);

  if (oldDID) {
    // Step 4: Re-encrypt with new PRF-derived secret
    const newUserSecret = prfSecret; // From passkey authentication

    // Delete old encrypted DID
    await didService.deactivateDID(user.accountId, oldUserSecret);

    // Create new encrypted DID with same content
    await didService.createDID(
      user.accountId,
      oldDID.entityType,
      newUserSecret, // NEW secret
      oldDID.publicKey[0].publicKeyBase58
    );

    console.log('DID migrated from Privy to passkey:', user.accountId);
  }

  // Step 5: Mark user as migrated
  await db.user.update({
    where: { id: user.id },
    data: { passkeyMigrated: true }
  });

  res.json({ success: true });
});
```

### Pitfall 5: Magic Link Security Weaknesses

**What goes wrong:** Magic link tokens predictable, tokens don't expire, replay attacks possible

**Why it happens:** Weak token generation (timestamp-based, sequential), missing expiration checks, no one-time-use enforcement

**How to avoid:**
1. Use crypto.randomBytes(32) for token generation (64 hex characters)
2. Enforce 15-minute expiration window
3. Mark token as "used" immediately after verification
4. Invalidate all previous tokens when generating new one

**Warning signs:**
- Multiple successful logins with same token
- Tokens working days after generation
- Sequential or predictable token patterns

**Code example:**
```typescript
// GOOD: Secure magic link implementation
import crypto from 'crypto';

export async function createMagicLink(email: string): Promise<string> {
  // Generate cryptographically secure random token
  const token = crypto.randomBytes(32).toString('hex'); // 64 hex chars

  // Short expiration window
  const expiresAt = new Date(Date.now() + 15 * 60 * 1000); // 15 minutes

  // Invalidate existing tokens (prevent token accumulation)
  await db.magicLinkToken.updateMany({
    where: { email, used: false },
    data: { used: true }
  });

  // Store new token
  await db.magicLinkToken.create({
    data: { token, email, expiresAt, used: false }
  });

  return token;
}

export async function verifyMagicLink(token: string): Promise<string | null> {
  const record = await db.magicLinkToken.findUnique({ where: { token } });

  // Comprehensive validation
  if (!record) return null;
  if (record.used) return null; // One-time use
  if (record.expiresAt < new Date()) return null; // Expired

  // Mark as used IMMEDIATELY (prevent race conditions)
  await db.magicLinkToken.update({
    where: { token },
    data: { used: true }
  });

  return record.email;
}
```

### Passkey Authentication with PRF for DID Operations

```typescript
// Backend: Generate authentication options with PRF
export async function generatePasskeyAuthentication(accountId: string) {
  const options = await generateAuthenticationOptions({
    rpID: 'bastion.near',
    userVerification: 'preferred',
    // Request PRF evaluation for DID secret derivation
    extensions: {
      prf: {
        eval: {
          // Use accountId as salt for deterministic derivation
          first: new TextEncoder().encode(`bastion-did-v1:${accountId}`)
        }
      }
    }
  });

  const challengeId = crypto.randomUUID();
  await storeChallenge(`auth:${challengeId}`, options.challenge);

  return { ...options, challengeId };
}

// Frontend: Authenticate with PRF
export async function authenticateWithPasskey() {
  const optionsRes = await fetch('/api/auth/passkey/auth-options', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' }
  });

  const { challengeId, ...webAuthnOptions } = await optionsRes.json();

  // Start authentication
  const credential = await startAuthentication({ optionsJSON: webAuthnOptions });

  // Extract PRF result (computed client-side)
  const prfResult = credential.clientExtensionResults?.prf?.results?.first;

  if (!prfResult) {
    console.warn('PRF not available - falling back to magic link');
    // Redirect to magic link flow
    return;
  }

  // Send authentication response with PRF result
  const verifyRes = await fetch('/api/auth/passkey/verify', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ challengeId, response: credential })
  });

  return verifyRes.json();
}

// Backend: Verify authentication and derive DID secret
export async function verifyPasskeyAuthentication(
  challengeId: string,
  response: AuthenticationResponseJSON
) {
  const expectedChallenge = await getChallenge(`auth:${challengeId}`);
  if (!expectedChallenge) throw new Error('No challenge found');

  // Find credential
  const credentialIdBuffer = Buffer.from(isoBase64URL.toBuffer(response.id));
  const credential = await db.passkeyCredential.findFirst({
    where: {
      credentialId: credentialIdBuffer
    },
    include: { user: true }
  });

  if (!credential) throw new Error('Credential not found');

  // Verify authentication
  const verification = await verifyAuthenticationResponse({
    response,
    expectedChallenge,
    expectedOrigin: 'https://bastion.near',
    expectedRPID: 'bastion.near',
    credential: {
      id: isoBase64URL.fromBuffer(Buffer.from(credential.credentialId)),
      publicKey: new Uint8Array(credential.publicKey),
      counter: Number(credential.counter),
      transports: JSON.parse(credential.transports)
    }
  });

  if (!verification.verified) {
    throw new Error('Authentication failed');
  }

  // Update counter
  await db.passkeyCredential.update({
    where: { id: credential.id },
    data: { counter: BigInt(verification.authenticationInfo.newCounter) }
  });

  // Extract PRF result for DID operations
  const prfOutput = response.clientExtensionResults?.prf?.results?.first;

  if (!prfOutput) {
    // PRF not available - can't perform DID operations
    // User still authenticated, but limited functionality
    return {
      verified: true,
      user: credential.user,
      prfAvailable: false
    };
  }

  // Convert PRF output to Uint8Array
  const userSecret = new Uint8Array(
    atob(prfOutput)
      .split('')
      .map(c => c.charCodeAt(0))
  );

  // Now use with existing DID system
  const accountId = credential.user.nearAccountId;
  const { deriveDIDBlindedKey, deriveEncryptionKey } = await import('./identity/blinded-keys.js');

  const blindedKey = deriveDIDBlindedKey(userSecret, accountId);
  const encryptionKey = deriveEncryptionKey(userSecret);

  // Create session with DID capabilities
  const sessionToken = await createSession(credential.user.id, {
    userSecret, // Store in Redis, not DB
    accountId,
    prfAvailable: true
  });

  return {
    verified: true,
    user: credential.user,
    sessionToken,
    prfAvailable: true
  };
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| OAuth providers (Privy, Auth0) | Passkeys (WebAuthn) | 2023-2025 mainstream | User owns credentials, no vendor lock-in, better UX (biometric), eliminates password databases |
| Password + 2FA | Passkey-only authentication | 2024-2026 | Single auth factor that's phishing-resistant, no SMS vulnerabilities |
| Credential ID as string | Credential ID as base64url (SimpleWebAuthn v13+) | 2024 | Breaking change - requires Buffer conversion for DB storage |
| HMAC-secret extension | PRF extension (W3C standardized) | 2023-2024 | Standardized API, better browser support, domain separation |
| Named NEAR accounts | NEAR implicit accounts | 2020 (NEP-71) | No registration friction, automatic creation on first transaction, perfect for self-sovereign identity |
| Privy user ID for key derivation | PRF-derived secrets | 2026 (this phase) | Self-sovereign key management, no dependency on external auth provider |

**Deprecated/outdated:**
- **FIDO U2F:** Replaced by FIDO2/WebAuthn (2019+), limited functionality, requires separate username/password
- **Master password for key derivation:** PRF extension eliminates need for user-memorized secrets
- **Platform-specific authenticator APIs:** WebAuthn standardizes across all platforms (iOS, Android, Windows, macOS)
- **Privy embedded wallets:** Moving to user-controlled passkey-based authentication

## Open Questions

Things that couldn't be fully resolved:

1. **PRF Extension Browser Compatibility Timeline**
   - What we know: Chrome/Edge full support (2024+), Safari 18+ supports with iCloud Keychain, Firefox prototype exists
   - What's unclear: Exact timeline for universal Firefox support, Android platform authenticator PRF support
   - Recommendation: Implement magic link fallback as primary recovery mechanism until PRF achieves 95%+ browser coverage. Monitor browser compatibility tables quarterly. Provide clear messaging when PRF unavailable.

2. **ED25519 vs P-256 for NEAR Implicit Accounts**
   - What we know: NEAR supports both ED25519 (hex) and Secp256k1 (keccak256-derived) implicit accounts. Most platform authenticators only support ES256 (P-256), not EdDSA.
   - What's unclear: Whether to force EdDSA (limiting device compatibility) or support P-256 with Secp256k1 conversion
   - Recommendation: Start with ES256 (P-256) for maximum compatibility, implement Secp256k1 implicit account derivation (`'0x' + keccak256(pubkey)[12:32].hex()`). Document that NEAR supports both formats. Consider EdDSA-only mode as premium feature for security-focused users with compatible hardware.

3. **DID Migration Strategy for Existing Privy Users**
   - What we know: Switching userSecret derivation source changes blinded keys, breaking DID access
   - What's unclear: Optimal migration window duration, whether to auto-migrate or require explicit user action
   - Recommendation: Implement 90-day dual-authentication window. During migration: (1) User logs in with Privy, (2) prompt to set up passkey, (3) background job decrypts DID with Privy-derived secret, re-encrypts with PRF-derived secret, (4) mark user as migrated, (5) after 90 days, force passkey setup or account suspension. Provide clear migration progress UI.

4. **Session Management Without Privy JWT**
   - What we know: Need to replace Privy's session tokens with custom implementation
   - What's unclear: Optimal session duration, refresh token strategy, Redis vs PostgreSQL storage
   - Recommendation: Use Redis for session storage (faster, automatic expiration). Session structure: `{ userId, accountId, prfAvailable, createdAt, expiresAt }`. Session duration: 7 days with sliding expiration. Refresh token strategy: generate new session token on each authenticated request if >50% expired. Store session ID in HttpOnly cookie.

5. **Account Recovery Edge Cases**
   - What we know: Email verification + passkey re-registration works for device loss
   - What's unclear: What happens if user loses email access AND passkey device simultaneously
   - Recommendation: Implement optional backup codes during onboarding (similar to 2FA backup codes). Store hashed backup codes in DB. User downloads codes, stores securely. If both email and passkey lost, backup code allows account recovery. Alternative: optional recovery contact (trusted friend/family email).
