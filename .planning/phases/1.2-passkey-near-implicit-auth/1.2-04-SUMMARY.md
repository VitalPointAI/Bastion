## Architecture Decisions

### 1. PRF Output as Direct userSecret (No Additional Derivation)

**Decision:** Use PRF output directly as userSecret for DID operations.

**Alternatives considered:**
- Apply additional HKDF derivation on PRF output → Rejected: unnecessary complexity
- Separate PRF-specific DID encryption → Rejected: duplication of logic
- Store PRF output in database → Rejected: security risk

**Rationale:**
- PRF extension already provides 32 bytes of deterministic cryptographic material
- HKDF-based blinding/encryption functions accept any 32-byte userSecret
- No need to know if userSecret came from NEAR key or PRF
- Maintains backward compatibility (existing DIDs work unchanged)

**Impact:** Clean integration without modifying DID encryption/blinding logic.

### 2. PRF Normalization Layer

**Decision:** Normalize PRF output to Uint8Array before use.

**Alternatives considered:**
- Require specific format from frontend → Rejected: frontend flexibility needed
- Handle formats in each function → Rejected: code duplication

**Rationale:**
- Browsers may return PRF output in different formats (Uint8Array, ArrayBuffer, base64url)
- Single normalization point ensures consistency
- Base64url handling for serialization across network

**Impact:** Frontend can send PRF output in most convenient format.

### 3. Backward Compatibility Maintained

**Decision:** Existing DID functions unchanged; PRF wrappers added alongside.

**Alternatives considered:**
- Modify existing functions to detect PRF vs NEAR → Rejected: unnecessary complexity
- Replace NEAR-based DIDs with PRF → Rejected: breaks existing users

**Rationale:**
- deriveDIDBlindedKey, deriveEncryptionKey work with any 32-byte userSecret
- New functions wrap existing logic with PRF-specific inputs
- Migration path clear: users can transition from NEAR to PRF gradually

**Impact:** No breaking changes to existing DID operations.

### 4. REST API Endpoints for PRF-Based DID

**Decision:** Add /register-prf and /resolve-prf alongside existing DID endpoints.

**Alternatives considered:**
- Modify existing /register endpoint → Rejected: different input contract
- Use same endpoint with format detection → Rejected: ambiguous API design

**Rationale:**
- Clear separation: PRF-based vs NEAR-based DID operations
- Different validation logic (PRF length check vs hex decoding)
- Easier for frontend to distinguish passkey path vs NEAR key path

**Impact:** Clean API design with explicit passkey-native path.

## Technical Highlights

### PRF-to-DID Integration

```typescript
// PRF output becomes userSecret (the KEY architectural decision)
export async function createDIDFromPRF(
  accountId: string,
  prfSecret: Uint8Array,  // 32-byte PRF output
  publicKeyBase58: string,
  entityType: 'Human' | 'Organization' | 'Device' | 'AI_Agent' = 'Human'
): Promise<{ did: string; blindedKey: string }> {
  // Validate PRF secret length
  if (prfSecret.length !== 32) {
    throw new Error(`Invalid PRF secret length: expected 32, got ${prfSecret.length}`);
  }

  // PRF secret IS the userSecret - no transformation needed
  const userSecret = prfSecret;

  // Existing DIDService works unchanged
  const didService = getDIDService();
  return didService.createDID(accountId, entityType, userSecret, publicKeyBase58);
}
```

### PRF Normalization

```typescript
// Handle various PRF output formats from browsers
export function normalizePRFOutput(
  prfOutput: Uint8Array | ArrayBuffer | string
): Uint8Array {
  if (prfOutput instanceof Uint8Array) {
    return prfOutput;
  }

  if (prfOutput instanceof ArrayBuffer) {
    return new Uint8Array(prfOutput);
  }

  // Base64url decode for network serialization
  if (typeof prfOutput === 'string') {
    const base64 = prfOutput.replace(/-/g, '+').replace(/_/g, '/');
    const padded = base64 + '='.repeat((4 - base64.length % 4) % 4);
    const binary = atob(padded);
    const bytes = new Uint8Array(binary.length);
    for (let i = 0; i < binary.length; i++) {
      bytes[i] = binary.charCodeAt(i);
    }
    return bytes;
  }

  throw new Error('Invalid PRF output format');
}
```

### PRF-Based Derivation (Optional Domain Separation)

```typescript
// Added to blinded-keys.ts for additional domain separation when desired
export function derivePRFUserSecret(prfOutput: Uint8Array, purpose: string): Uint8Array {
  const salt = utf8ToBytes('bastion-prf-secret');
  const info = utf8ToBytes(purpose);
  return hkdf(sha256, prfOutput, salt, info, 32);
}
```

### REST API Endpoints

**POST /api/identity/register-prf**
```typescript
// Body: { accountId, prfSecret (base64url), publicKeyBase58, entityType? }
// Response: { did, blindedKey, entityType }
router.post('/register-prf', async (req, res) => {
  const { accountId, prfSecret, publicKeyBase58, entityType } = req.body;

  // Normalize PRF secret from various formats
  const normalizedSecret = normalizePRFOutput(prfSecret);

  // Validate 32-byte length
  if (normalizedSecret.length !== 32) {
    return res.status(400).json({
      error: `Invalid PRF secret length: expected 32, got ${normalizedSecret.length}`
    });
  }

  // Create DID using PRF-derived secret
  const result = await createDIDFromPRF(
    accountId,
    normalizedSecret,
    publicKeyBase58,
    entityType || 'Human'
  );

  res.json({ did: result.did, blindedKey: result.blindedKey, entityType });
});
```

**POST /api/identity/resolve-prf**
```typescript
// Body: { accountId, prfSecret (base64url) }
// Response: { didDocument, found }
router.post('/resolve-prf', async (req, res) => {
  const { accountId, prfSecret } = req.body;

  const normalizedSecret = normalizePRFOutput(prfSecret);

  if (normalizedSecret.length !== 32) {
    return res.status(400).json({ error: 'Invalid PRF secret length' });
  }

  const document = await resolveDIDFromPRF(accountId, normalizedSecret);

  res.json({
    didDocument: document,
    found: document !== null
  });
});
```
