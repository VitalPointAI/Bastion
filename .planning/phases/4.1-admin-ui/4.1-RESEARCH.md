# Phase 4.1: Admin UI - Research

**Researched:** 2026-01-19
**Domain:** React admin configuration interface
**Confidence:** HIGH

<research_summary>
## Summary

Researched the React ecosystem for building an admin configuration UI that integrates with the existing BASTION backend admin API. The existing codebase uses React 19 + Vite + TypeScript with minimal dependencies and custom CSS following a military/tactical command-center aesthetic.

The recommended approach is to keep the stack minimal and consistent with the existing codebase patterns:
- **React Hook Form + Zod** for form handling (Zod already used in backend)
- **TanStack Table** for data tables (audit logs, OSINT sources)
- **react-tabs** for tabbed navigation between config sections
- **Custom CSS** extending the existing command-center design tokens

This avoids introducing heavy UI frameworks (MUI, Ant Design) while maintaining consistency with the existing component patterns in DAODashboard and StrategicDashboard.

**Primary recommendation:** Use react-hook-form + @hookform/resolvers/zod for forms, TanStack Table for data display, react-tabs for navigation, and extend existing CSS custom properties for styling. No new styling framework needed.
</research_summary>

### Pattern 1: React Hook Form with Zod
**What:** Uncontrolled form with type-safe validation
**When to use:** All config editing forms
**Example:**
```typescript
// Source: react-hook-form docs + @hookform/resolvers
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';

const LLMConfigSchema = z.object({
  provider: z.enum(['anthropic', 'openai', 'azure-openai', 'local']),
  models: z.object({
    extraction: z.string().min(1),
    analysis: z.string().min(1),
  }),
  maxRequestsPerMinute: z.number().min(1).max(1000),
});

type LLMConfig = z.infer<typeof LLMConfigSchema>;

function LLMConfigPanel() {
  const { register, handleSubmit, formState: { errors, isDirty } } = useForm<LLMConfig>({
    resolver: zodResolver(LLMConfigSchema),
    defaultValues: async () => adminService.getLLMConfig(),
  });

  const onSubmit = async (data: LLMConfig) => {
    await adminService.updateLLMConfig(data);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <select {...register('provider')}>
        <option value="anthropic">Anthropic</option>
        <option value="openai">OpenAI</option>
      </select>
      {errors.provider && <span className="error">{errors.provider.message}</span>}
      {/* ... more fields */}
      <button type="submit" disabled={!isDirty}>Save Changes</button>
    </form>
  );
}
```

### Pattern 2: TanStack Table for OSINT Sources
**What:** Headless table with custom rendering
**When to use:** Tabular data with CRUD operations
**Example:**
```typescript
// Source: TanStack Table docs
import { useReactTable, getCoreRowModel, flexRender } from '@tanstack/react-table';
import type { ColumnDef } from '@tanstack/react-table';

interface OSINTSource {
  id: string;
  name: string;
  type: string;
  enabled: boolean;
  credibilityRating: number;
}

const columns: ColumnDef<OSINTSource>[] = [
  { accessorKey: 'name', header: 'Name' },
  { accessorKey: 'type', header: 'Type' },
  {
    accessorKey: 'enabled',
    header: 'Status',
    cell: ({ getValue }) => (
      <span className={`status-badge ${getValue() ? 'enabled' : 'disabled'}`}>
        {getValue() ? 'Enabled' : 'Disabled'}
      </span>
    ),
  },
  {
    id: 'actions',
    cell: ({ row }) => (
      <div className="actions">
        <button onClick={() => onEdit(row.original)}>Edit</button>
        <button onClick={() => onDelete(row.original.id)}>Delete</button>
      </div>
    ),
  },
];

function OSINTSourceTable({ data }: { data: OSINTSource[] }) {
  const table = useReactTable({ data, columns, getCoreRowModel: getCoreRowModel() });

  return (
    <table className="admin-table">
      <thead>
        {table.getHeaderGroups().map(headerGroup => (
          <tr key={headerGroup.id}>
            {headerGroup.headers.map(header => (
              <th key={header.id}>
                {flexRender(header.column.columnDef.header, header.getContext())}
              </th>
            ))}
          </tr>
        ))}
      </thead>
      <tbody>
        {table.getRowModel().rows.map(row => (
          <tr key={row.id}>
            {row.getVisibleCells().map(cell => (
              <td key={cell.id}>
                {flexRender(cell.column.columnDef.cell, cell.getContext())}
              </td>
            ))}
          </tr>
        ))}
      </tbody>
    </table>
  );
}
```

### Anti-Patterns to Avoid
- **Using global state for form data:** Form state should stay in react-hook-form, not in Zustand/Redux
- **Building custom table components from scratch:** TanStack Table handles sorting, filtering, pagination
- **Adding MUI/Ant Design for just admin:** Heavy frameworks add bundle bloat for simple config screens
- **Storing API keys in frontend state:** Only display masked keys from backend, never store full keys
- **Over-fetching config on every tab switch:** Cache config data, invalidate on save

<dont_hand_roll>
## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Form validation | Custom validation logic | react-hook-form + zod | Complex edge cases, async validation, touched states |
| Data tables | Custom <table> with loops | TanStack Table | Sorting, filtering, pagination, column resizing |
| Tab navigation | Custom click handlers | react-tabs | Keyboard navigation, ARIA roles, focus management |
| API key masking | Custom mask function | Backend handles this | Security: never send full keys to frontend |
| Optimistic updates | Manual state rollback | Use mutation + refetch pattern | Race conditions, error recovery is complex |
| Error boundary | try/catch in components | React ErrorBoundary | Proper error recovery, fallback UI |

**Key insight:** Admin UIs seem simple but have many accessibility and UX edge cases. Libraries like react-hook-form and TanStack Table have solved these problems across thousands of implementations. Custom solutions lead to missed keyboard navigation, broken validation states, and poor accessibility.
</dont_hand_roll>

<common_pitfalls>
## Common Pitfalls

### Pitfall 1: Storing Sensitive Data in Frontend State
**What goes wrong:** API keys, secrets stored in React state get exposed in React DevTools, browser memory
**Why it happens:** Backend returns full config including encrypted fields after masking
**How to avoid:** Backend should ALWAYS mask sensitive fields before sending to frontend. Never send unmasked API keys. Use `****...last4` pattern.
**Warning signs:** Config responses include full API key strings

### Pitfall 2: Form Re-renders on Every Keystroke
**What goes wrong:** Entire form re-renders on each input change, causing lag and flickering
**Why it happens:** Using controlled components with useState for each field
**How to avoid:** Use react-hook-form's uncontrolled mode (register) instead of controlled (Controller) where possible
**Warning signs:** Typing feels sluggish, React Profiler shows form re-renders on keystroke

### Pitfall 3: Missing Loading and Error States
**What goes wrong:** Form submits with no feedback, errors silently fail
**Why it happens:** Focus on happy path during development
**How to avoid:** Always implement isSubmitting state, show loading indicator, display error messages prominently
**Warning signs:** Users clicking save multiple times, confusion about whether action succeeded

### Pitfall 4: Stale Config Data After Save
**What goes wrong:** User saves config, UI shows old values until page refresh
**Why it happens:** Form displays cached values, doesn't refetch after mutation
**How to avoid:** After successful save, either update local state with response OR refetch config
**Warning signs:** "I saved it but it shows the old value"

### Pitfall 5: Breaking Existing Styles
**What goes wrong:** New admin components don't match command-center aesthetic
**Why it happens:** Using library's default styles or different CSS approach
**How to avoid:** Use existing CSS custom properties (--bg-primary, --accent-blue, etc.), extend existing component patterns
**Warning signs:** Admin section looks like a different app

### Pitfall 6: Not Handling ADMIN_DIDS Permission
**What goes wrong:** Non-admin users see admin nav or get confusing 403 errors
**Why it happens:** Admin check only on backend, frontend shows admin UI to everyone
**How to avoid:** Check admin status on frontend, conditionally render admin nav item, show clear "Access Denied" for 403
**Warning signs:** Users clicking Admin and seeing error screen
</common_pitfalls>

### Admin Service Pattern
```typescript
// Source: Project pattern from lib/governance-service.ts
const API_BASE = import.meta.env.VITE_API_URL || 'http://localhost:3000';

interface AdminConfig {
  llm: LLMProviderConfig;
  agents: AgentConfig;
  workflow: WorkflowConfig;
}

export const adminService = {
  async getLLMConfig(): Promise<LLMProviderConfig> {
    const res = await axios.get(`${API_BASE}/api/admin/config/llm`, {
      headers: { 'X-DID': getUserDID() },
    });
    return res.data;
  },

  async updateLLMConfig(config: Partial<LLMProviderConfig>, reason?: string): Promise<LLMProviderConfig> {
    const res = await axios.put(
      `${API_BASE}/api/admin/config/llm`,
      { ...config, reason },
      { headers: { 'X-DID': getUserDID() } }
    );
    return res.data;
  },

  async getOSINTSources(): Promise<{ count: number; sources: OSINTSourceConfig[] }> {
    const res = await axios.get(`${API_BASE}/api/admin/osint-sources`, {
      headers: { 'X-DID': getUserDID() },
    });
    return res.data;
  },

  async getAuditLog(params?: { category?: string; limit?: number }): Promise<{ entries: ConfigAuditEntry[] }> {
    const res = await axios.get(`${API_BASE}/api/admin/config/audit`, {
      params,
      headers: { 'X-DID': getUserDID() },
    });
    return res.data;
  },
};
```

## State of the Art (2025-2026)

What's changed recently:

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Formik | react-hook-form | 2023+ | RHF is lighter, faster, better TS support |
| react-table v7 | @tanstack/react-table v8 | 2022 | Headless-first, framework-agnostic |
| Custom validation | Zod + resolver | 2023+ | Type inference, schema-first validation |
| Full admin frameworks | Headless primitives | 2024+ | Mix-and-match approach preferred |
| MUI Data Grid | TanStack Table | Preference shift | More control, smaller bundle |

**New tools/patterns to consider:**
- **React 19 useOptimistic**: For optimistic UI updates, but complex to use correctly
- **Standard Schema (zodResolver v5)**: Unified validation resolver interface
- **Ark UI**: Alternative to Radix, but unnecessary for this scope

**Deprecated/outdated:**
- **Formik**: Still works but react-hook-form has won mindshare
- **Class components for forms**: Hooks-based patterns are standard
- **Redux Form**: Ancient, don't use
</sota_updates>
